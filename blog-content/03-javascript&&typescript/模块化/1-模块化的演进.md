# 模块化的演进（从无到 ESM）

参考文档：
- MDN JavaScript 模块：https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Guide/Modules

## 一、为什么需要模块化

早期的 JavaScript 程序都很小，通常只是给页面加一点交互，直接写在 `<script>` 标签里就够了。但随着 Web 应用越来越复杂、Node.js 等运行环境出现，一个项目动辄上万行代码，「把所有代码堆在一起」带来了几个绕不开的问题：

- **全局污染**：所有变量/函数都挂在全局作用域（`window`）下，不同文件的同名变量会互相覆盖。
- **依赖混乱**：文件之间的依赖关系靠 `<script>` 的书写顺序来保证，顺序错了就报 `xxx is not defined`。
- **难以复用与维护**：没有清晰的「导出/导入」边界，无法明确一个文件对外提供了什么、依赖了什么。

**模块化**就是为了解决这些问题：把程序拆分成一个个独立的、有明确输入输出、拥有独立作用域的模块，按需导入组合。核心价值可以概括为三点：**作用域隔离、依赖管理、代码复用**。

下面按时间线看看模块化是怎么一步步演进到今天的 ES Modules 的。

## 二、演进时间线总览

| 阶段 | 方案 | 环境 | 核心特点 |
|---|---|---|---|
| 无模块时代 | 全局函数 / `<script>` 堆叠 | 浏览器 | 全局污染、依赖靠顺序 |
| 命名空间 | 对象字面量 | 浏览器 | 缓解命名冲突，但仍暴露内部 |
| 模块雏形 | IIFE（立即执行函数） | 浏览器 | 私有作用域 + 暴露公共接口 |
| 社区规范（服务端） | CommonJS | Node.js | **同步**加载、值拷贝 |
| 社区规范（浏览器） | AMD / CMD | 浏览器 | **异步**加载，依赖前置/就近 |
| 通用兼容 | UMD | 浏览器 + Node | 一份代码适配多环境 |
| **官方标准** | **ES Modules (ESM)** | 浏览器 + Node | 语言原生、静态分析、Tree Shaking |

## 三、无模块时代与命名空间

最原始的写法就是把代码全丢进 `<script>`，或拆成多个文件用 `src` 引入：

```html
<script src="utils.js"></script>
<script src="main.js"></script>
```

问题很明显：`utils.js` 必须在 `main.js` 之前，且两者的变量共享同一个全局作用域。

后来人们用**命名空间（对象字面量）**做了缓解，把相关功能塞进一个全局对象里，减少全局变量数量：

```js
const MyApp = {
  utils: {
    add(a, b) { return a + b }
  }
}
MyApp.utils.add(1, 2)
```

但它治标不治本：内部实现依然完全暴露，任何人都能改 `MyApp.utils`，也没有真正的私有性。

## 四、IIFE：模块的雏形

IIFE（Immediately Invoked Function Expression，立即执行函数）利用**函数作用域**创造了「私有空间」，只把需要暴露的接口 `return` 出去，这就是模块化思想的雏形：

```js
const counterModule = (function () {
  // 私有变量，外部访问不到
  let count = 0

  // 只暴露公共接口
  return {
    increment() { count++ },
    getCount() { return count },
  }
})()

counterModule.increment()
counterModule.getCount() // 1
// counterModule.count 是 undefined —— 真正的私有
```

还可以通过参数「依赖注入」，把外部依赖显式传进来（比如把 jQuery 传进模块）。IIFE 解决了作用域隔离和私有性，但**依赖管理仍然要靠手动**，没有统一的加载机制。

## 五、CommonJS：服务端的同步方案

2009 年随 Node.js 流行起来的 **CommonJS** 是第一个被广泛采用的模块规范。它规定：**每个文件就是一个模块**，用 `module.exports` / `exports` 导出，用 `require()` 导入。

```js
// math.js
function add(a, b) {
  return a + b
}
module.exports = { add }

// app.js
const math = require('./math.js')
console.log(math.add(2, 3)) // 5
```

核心特点：

- **同步加载**：`require()` 会阻塞后续代码，直到模块加载执行完毕。因为服务端模块都在本地磁盘，读取快，同步不影响性能。
- **值拷贝**：导出的是值的**拷贝**（对象则是引用的拷贝）。导入后，原模块内部对基本类型的改动不会反映到导入方。
- **运行时加载**：依赖关系在代码**执行时**才动态解析，无法在编译阶段做静态优化。
- **缓存（单例）**：同一个模块只会执行一次，之后 `require` 直接返回缓存的 `module.exports`。

> `module.exports` vs `exports`：`exports` 只是 `module.exports` 的一个引用。可以用 `exports.add = ...` 挂属性，但**不能**直接 `exports = {...}` 整体赋值（会切断引用，导出失效）；整体导出要用 `module.exports = {...}`。

**局限**：同步加载在浏览器端行不通——浏览器加载文件要走网络，同步会导致页面「假死」。所以浏览器端需要异步方案。

## 六、AMD 与 CMD：浏览器的异步方案

### AMD（代表：RequireJS）
针对浏览器设计，理念是**异步加载 + 依赖前置**：定义模块时就声明好所有依赖，加载完再执行回调。

```js
// 定义模块
define(['jquery'], function ($) {
  function myFunc() {
    $('#content').html('Hello, AMD!')
  }
  return { myFunc }
})

// 加载并使用
require(['myModule'], function (myModule) {
  myModule.myFunc()
})
```

### CMD（代表：Sea.js）
国内发展出的规范，理念是**依赖就近 + 延迟执行**：在真正用到时才 `require`，语法更接近 CommonJS。

```js
define(function (require, exports, module) {
  const $ = require('jquery') // 依赖就近，用到才引
  exports.someMethod = function () {
    $('#content').html('Hello, CMD!')
  }
})
```

**AMD vs CMD 的核心区别**：
- 依赖声明：AMD **依赖前置**（定义时声明全部依赖）；CMD **依赖就近**（用到才声明）。
- 执行时机：AMD 依赖加载完**立即执行**；CMD 加载后不执行，`require` 时才执行。

## 七、UMD：通用兼容方案

**UMD（Universal Module Definition）**不是一个新规范，而是一种**代码包装模式**：通过判断当前环境，让同一份代码在 AMD、CommonJS、浏览器全局变量三种环境下都能用。开源库（如早期的 React、Vue、lodash 发行包）常用它来发布。

```js
(function (root, factory) {
  if (typeof define === 'function' && define.amd) {
    define(['jquery'], factory)              // AMD 环境
  } else if (typeof module === 'object' && module.exports) {
    module.exports = factory(require('jquery')) // CommonJS 环境
  } else {
    root.MyLibrary = factory(root.jQuery)    // 浏览器全局
  }
}(this, function ($) {
  function myFunc() { /* ... */ }
  return { myFunc }
}))
```

## 八、ES Modules：官方原生标准

ES2015（ES6）终于给 JavaScript 带来了**语言层面的原生模块系统 ESM**，用 `export` 导出、`import` 导入，现代浏览器和 Node.js（14+）都原生支持。

```js
// math.js
export const PI = 3.14159
export function add(x, y) {
  return x + y
}
export default class Calculator {
  multiply(x, y) { return x * y }
}

// app.js
import Calculator, { PI, add } from './math.js'
```

在浏览器中通过 `type="module"` 使用：

```html
<script type="module" src="app.js"></script>
<!-- 或内联 -->
<script type="module">
  import { add } from './math.js'
  console.log(add(1, 2))
</script>
```

ESM 的关键特性：

- **静态化**：`import`/`export` 只能在模块顶层，编译阶段（执行前）就能确定依赖关系与输入输出。这让**静态分析**和 **Tree Shaking（摇树优化，删除未使用代码）**成为可能。
- **值的引用（实时绑定）**：导入的是导出值的**只读引用**，而非拷贝。原模块内部值变化，导入方能感知到；但导入方不能给导入的变量重新赋值。
- **模块默认严格模式**：自动 `"use strict"`。
- **自动 defer**：`type="module"` 脚本默认延迟执行（等 HTML 解析完，按顺序执行）。
- **独立作用域**：模块顶层的变量是模块作用域私有的，不会污染全局。
- **只执行一次**：同一模块被多次导入，只会执行一次，共享同一份实例。
- **需要服务器环境 + CORS**：出于安全，模块不能通过 `file://` 直接打开，需经 Web 服务器加载，且服务器要返回正确的 MIME 类型（`text/javascript`）。

> 打包工具（webpack / Vite 等）在原生 ESM 时代依然有价值：代码分割、压缩、Tree Shaking、处理非 JS 资源、兼容旧浏览器等。

## 九、CommonJS vs ESM 速查

| 维度 | CommonJS | ES Modules |
|---|---|---|
| 语法 | `require` / `module.exports` | `import` / `export` |
| 加载时机 | 运行时动态加载 | 编译时静态分析（`import()` 可动态） |
| 加载方式 | 同步 | 异步（浏览器） |
| 导出值 | 值的拷贝 | 值的引用（实时绑定） |
| 顶层 `this` | 指向 `module.exports` | `undefined` |
| Tree Shaking | 不友好 | 友好 |
| 主要环境 | Node.js（服务端） | 浏览器 + Node.js，未来主流 |

> 这两者的语法、加载机制、循环依赖处理等更细致的对比，可在后续单独篇章展开（本篇聚焦「演进脉络」）。

## 十、小结

模块化的演进，本质是围绕**作用域隔离**和**依赖管理**这两个核心诉求不断改进的过程：

> 全局堆叠 → 命名空间 → IIFE（私有作用域）→ CommonJS（服务端同步）/ AMD·CMD（浏览器异步）→ UMD（通用兼容）→ **ESM（语言原生标准）**

如今 **ESM 是绝对主流**：写业务代码优先用 `import`/`export`；只有在特定 Node 老项目或兼容场景才会遇到 CommonJS、UMD。理解这条演进线，能帮你看懂为什么各种规范会长成现在这样，也更容易理解构建工具在其中扮演的角色。
