# AI 友好前端架构

资料来源：[AI 友好前端架构的 16 个原则](https://bytetech.info/articles/7630824916388708379#LvbhdBimioqpuKxnywFcYwNcnpb)

## 1. 是什么

AI 友好前端架构，是指让 AI 更容易理解、定位、生成和修改代码的工程组织方式。

它不是单独给 AI 加一层工具，而是把传统工程里的目录、类型、文档、约束、测试和验收标准整理得更清晰，让 AI 在有限上下文中稳定工作。

## 2. 解决什么问题

| 问题 | 影响 |
|---|---|
| 仓库拆散 | AI 难以跨仓追踪组件、类型、请求和调用链 |
| 目录语义弱 | AI 需要大量搜索才能定位业务代码 |
| 类型不严格 | AI 只能猜字段和分支，生成代码不稳定 |
| 文档过长或过期 | AI 被无关信息干扰，甚至被错误信息误导 |
| 规则不可执行 | AI 不知道如何自检，容易停在“看起来正确” |
| 示例缺失 | AI 缺少可模仿的本地写法，容易套用通用模式 |

## 3. 技术原理

AI 写代码时依赖三类线索：

| 线索 | 对应工程能力 |
|---|---|
| 结构线索 | Monorepo、语义化目录、短引用链路 |
| 语义线索 | 清晰命名、严格类型、导出的边界类型 |
| 行为线索 | 样板文件、测试用例、可执行验收命令 |

这些线索越清晰，AI 需要猜测的部分越少，生成代码越接近仓库既有风格。

## 4. 16 个原则速览

| 原则 | 核心作用 | 落地要点 |
|---|---|---|
| 使用 Monorepo | 给 AI 一张完整代码地图 | `apps` 承载应用，`packages` 承载共享模块，依赖单向 |
| 选择主流技术栈 | 借助 AI 训练数据先验 | 优先 React、TypeScript、CSS Modules 等高覆盖技术 |
| 开启 TS 严格模式 | 用类型减少猜测 | `strict: true`，限制 `any`，开启构建期类型检查 |
| 兼容多 Agent | 让团队工具读取同一套上下文 | `.agents` 作为源目录，其他 Agent 目录用软链分发 |
| 写好 `AGENTS.md` | 给 AI 项目入职手册 | 只写高频全局信息，控制在百行量级 |
| 精装 Skills | 按需加载详细规范 | 少装高频 Skill，`description` 写清触发场景 |
| 统一编码约束 | 让风格问题自动暴露 | 全仓一份 Biome / Lint 配置，保留能防 bug 的规则 |
| 明确验收标准 | 形成编码到验证闭环 | Lint、Build、Test 三层验收写进上下文 |
| 语义化目录 | 路径即地图 | 避免 `helpers`、`misc`、`module1` 等弱语义目录 |
| 语义化命名 | 名字直接表达意图 | 不滥用缩写，布尔值用 `is/has/should` 前缀 |
| 提供标准样板文件 | 一个好范例胜过长规范 | 为页面、组件、请求、Hook、测试提供黄金参考 |
| 充分导出类型 | 类型就是跨模块合同 | Props、API、回调参数、共享实体类型从入口可达 |
| 缩短引用链路 | 降低追踪成本 | 应用内少用 barrel，包入口保留一层即可 |
| 测试即行为文档 | 用例告诉 AI 正确行为 | 优先覆盖边界条件、错误处理、核心纯函数 |
| 注释写决策 | 记录 AI 猜不到的原因 | 注释解释业务约束、权衡和 workaround，不翻译代码 |
| 文档保持新鲜 | 防止上下文反向误导 | CI 检查文档路径、命令、样板是否仍有效 |

## 5. 对前端工程的启发

| 工程动作 | AI 友好价值 |
|---|---|
| 把目录结构整理成稳定约定 | AI 可以先按路径推断职责，再读文件 |
| 把编码规范拆成 Skill | 避免每次对话加载冗长细则 |
| 把常用命令写进 `AGENTS.md` | AI 能独立完成验证，而不是只改代码 |
| 把边界类型显式导出 | AI 修改消费方时不用打开实现文件反推 |
| 把核心行为写成测试 | AI 有明确红绿反馈，不靠主观判断 |

## 6. 面试表达

| 问题 | 回答要点 |
|---|---|
| 什么是 AI 友好架构？ | 让 AI 能通过结构、类型、文档和测试快速理解工程并稳定修改代码的架构方式 |
| 为什么 Monorepo 更适合 AI？ | 上下游依赖、共享组件和类型都在同一上下文里，AI 可以跨模块追踪 |
| `AGENTS.md` 应该写什么？ | 项目简介、技术栈、目录结构、常用命令、变更约定和 Skill 索引 |
| 为什么不能把所有规范都放进 `AGENTS.md`？ | 每次对话都会加载，过长会浪费上下文并干扰注意力 |
| 类型系统为什么重要？ | 类型是 AI 理解输入、输出、可选字段和分支收窄的直接线索 |
| 测试为什么也是 AI 文档？ | 测试用例用输入输出定义行为，比自然语言更精确，并且可执行验证 |

## 7. 落地检查清单

- 仓库是否有根级 `AGENTS.md`，且内容足够短。
- 应用和共享包是否有独立上下文说明。
- 编码规范是否从 `AGENTS.md` 拆到 Skill。
- 目录名是否能直接表达业务或技术职责。
- 共享类型是否能从稳定入口导入。
- 是否有标准样板文件供 AI 模仿。
- 是否有 Lint、Build、Test 的明确命令。
- 文档中引用的路径和命令是否有自动校验。
