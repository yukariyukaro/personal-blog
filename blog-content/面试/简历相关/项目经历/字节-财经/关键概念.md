# 字节财经项目关键概念

本文用于面试复盘和项目经历表达，重点不是背平台操作，而是能说明：

```text
它是什么 -> 解决什么问题 -> 技术原理是什么 -> 在前端项目里怎么理解
```

## 1. 泳道

### 是什么

泳道是字节内部常见的环境隔离机制。它允许在同一个大环境中，为某个服务部署一份独立代码版本，并通过流量标记让指定请求进入这份代码。

可以把它理解成：

> 在不影响基准环境的前提下，为某个需求创建一条“只让特定流量通过”的测试通道。

常见概念：

| 概念 | 说明 |
|------|------|
| 基准环境 | 默认流量进入的稳定版本 |
| BOE 泳道 | 通常面向测试环境，使用测试数据 |
| PPE 泳道 | 通常与线上环境共享数据，用于更接近真实线上链路的验证 |
| 流量染色 | 给请求打标，让链路识别它应该进入哪条泳道 |

### 解决什么问题

没有泳道时，一个服务在同一环境里通常只能跑一个代码版本。新需求要联调，就容易影响其他人。

泳道解决的是：

| 问题 | 泳道的作用 |
|------|------------|
| 多需求并行联调 | 不同需求走不同泳道 |
| 避免影响基准环境 | 只有被染色的请求进入新版本 |
| 端到端链路验证 | 请求可沿调用链进入对应泳道服务 |
| 提前发现线上链路问题 | PPE 更接近线上真实环境 |

### 技术原理

泳道的核心是 **流量标记 + 链路透传 + 路由选择**。

```text
用户请求
  ↓
请求头携带泳道标记
  ↓
入口服务识别标记
  ↓
标记写入上下文
  ↓
RPC / HTTP 调用继续透传标记
  ↓
下游服务优先路由到同名泳道
  ↓
如果下游没有该泳道，则回退到基准环境
```

常见 HTTP 标记类似：

| Header | 作用 |
|--------|------|
| `x-tt-env` | 指定目标泳道名 |
| `x-use-ppe` | 标记是否使用 PPE |

### 面试表达

在财经项目里，可以这样说：

> 我使用泳道做需求联调和灰度前验证。它本质上是通过请求染色把流量导向某个独立部署的服务版本，请求标记会在后端调用链中透传。这样可以在不影响基准环境的情况下验证新代码。但 PPE 可能共享线上数据，所以涉及写操作时要特别谨慎。

## 2. 容器

### 是什么

“容器”这个词在不同语境下含义不同：

| 语境 | 含义 |
|------|------|
| 云原生容器 | Docker / Kubernetes 里的运行单元，用来打包应用和依赖 |
| 客户端跨端容器 | App 内承载 H5 / Lynx 页面的一层运行环境 |

在字节财经前端项目里，更多讨论的是 **客户端跨端容器**。

客户端容器可以理解成：

> App 内专门负责加载、运行、管理前端页面的 Native 外壳。

更抽象地说，容器就是：

> 给某类内容提供一套可运行环境，并屏蔽底层复杂细节的载体。

所以，Docker 是容器，AnnieX 这类客户端运行环境也可以叫容器。它们不是同一类技术，但共享同一个抽象：**把复杂底层能力封装起来，让上层内容可以稳定运行**。

如果是 H5 页面，底层通常依赖 `WebView`；如果是 Lynx 页面，底层依赖 `LynxView`。业务容器会在这些底层视图之上继续封装路由、资源加载、JSB、监控、性能优化等能力。

### 和 Docker 容器的区别

Docker 容器和 AnnieX 这类客户端容器，不在同一个技术层级。

| 对比 | Docker 容器 | AnnieX 这类客户端容器 |
|------|-------------|----------------------|
| 所在层级 | 服务端 / 云原生 / 操作系统层 | 客户端 App / 跨端页面运行层 |
| 承载对象 | 一个应用进程及其依赖 | 一个 H5 / Lynx 页面及其运行能力 |
| 底层依赖 | Linux namespace、cgroups、镜像、容器运行时 | WebView、LynxView、Native SDK、JSBridge、资源加载器 |
| 解决问题 | 应用部署一致性、环境隔离、资源隔离 | App 内如何打开、运行、调试、监控跨端页面 |
| 典型目标 | “这段后端服务在哪都能跑” | “这张前端页面能在 App 里稳定、高性能地跑” |

可以这样类比：

```text
Docker 容器：后端应用的运行盒子
AnnieX 容器：App 内跨端页面的运行盒子
```

因此，看到“容器”这个词时，要先判断它所在的语境：

| 问题 | 判断 |
|------|------|
| 在讲服务器部署、镜像、K8s、Pod | 多半是 Docker / 云原生容器 |
| 在讲 App、H5、Lynx、WebView、JSB | 多半是客户端跨端容器 |

### 解决什么问题

前端页面运行在 App 里时，不能只靠浏览器能力。它还需要：

| 需求 | 容器提供的能力 |
|------|----------------|
| 打开页面 | 解析 schema，创建 WebView / LynxView |
| 使用端能力 | 通过 JSBridge 调用 Native 能力 |
| 加载资源 | 加载 HTML、Lynx bundle、离线包、图片等 |
| 注入上下文 | 注入用户、设备、主题、实验参数等 GlobalProps |
| 性能优化 | 预加载、预取、预渲染、View 复用 |
| 质量治理 | 监控、错误页、日志、性能指标 |

### 技术原理

客户端容器通常分为几层：

```text
业务代码
  ↓
业务容器层：统一对外接口、业务定制、生命周期
  ↓
基础容器层：WebView / LynxView 加载能力
  ↓
Native 能力层：路由、网络、存储、JSB、监控、资源管理
```

一个简化的页面打开流程：

```text
schema 链接
  ↓
容器解析参数
  ↓
选择 WebView 或 LynxView
  ↓
加载资源
  ↓
注入初始化数据 / GlobalProps
  ↓
建立 JSBridge
  ↓
页面渲染并上报监控
```

### 面试表达

> 我理解的容器不是 Docker 那类云原生容器，而是 App 内承载跨端页面的运行环境。它屏蔽 WebView、LynxView、路由、JSB、资源加载和监控差异，让前端能用统一方式开发端内页面。

## 3. WebView / LynxView

### 是什么

`WebView` 和 `LynxView` 都是客户端里的原生视图组件。它们不是业务容器本身，而是业务容器底层真正用来承载页面内容的视图。

可以先这样理解：

```text
H5 页面   -> WebView
Lynx 页面 -> LynxView
```

| 概念 | 本质 | 承载内容 |
|------|------|----------|
| WebView | App 内嵌的浏览器视图 | HTML、CSS、JavaScript |
| LynxView | App 内嵌的 Lynx 渲染视图 | Lynx bundle / template.js |

`WebView` 更像 App 里嵌入的一块“小浏览器”。它有浏览器内核，能解析 HTML、CSS、JavaScript，也有 `window`、`document`、DOM 等 Web 运行环境。

`LynxView` 不是浏览器。它是 Lynx SDK 提供的原生渲染容器，用来加载 Lynx 产物，并通过 Lynx 引擎构建 UI 树、计算布局，最终映射到端上的原生视图或自渲染管线。

### 解决什么问题

它们解决的是 **前端页面如何在 App 内真正跑起来** 的问题。

| 问题 | WebView / LynxView 的作用 |
|------|---------------------------|
| App 如何展示 H5 页面 | 创建 WebView，加载 URL 或离线 HTML 资源 |
| App 如何展示 Lynx 页面 | 创建 LynxView，加载 template.js / Lynx bundle |
| 页面如何拿到端能力 | 配合 JSBridge / Native Module |
| 页面如何进入 Native 页面体系 | 作为一个原生 View 被加到 Activity / Fragment / ViewController 中 |
| 页面如何参与性能监控 | 暴露加载、渲染、错误、生命周期等节点 |

所以，业务容器通常不直接“画页面”，而是：

```text
业务容器
  ↓
创建 WebView 或 LynxView
  ↓
向底层视图传入资源、数据、JSB、生命周期回调
  ↓
底层视图完成页面加载和渲染
```

### 技术原理

#### WebView 的原理

`WebView` 底层依赖系统或宿主定制的浏览器内核。

简化流程：

```text
容器拿到页面 URL / HTML
  ↓
WebView 加载资源
  ↓
浏览器内核解析 HTML / CSS / JS
  ↓
构建 DOM / CSSOM
  ↓
执行 JavaScript
  ↓
布局、绘制、合成
  ↓
展示在 App 页面中
```

WebView 和 Native 通信通常依赖 JSBridge：

| 方向 | 常见方式 |
|------|----------|
| JS 调 Native | 注入对象、拦截 scheme、message handler |
| Native 调 JS | `evaluateJavascript` / 注入脚本 |

在财经跨端页面里，WebView 还常配合离线资源加载器使用，例如通过资源拦截把线上 URL 映射到 Gecko / Forest 本地资源，减少网络加载耗时。

#### LynxView 的原理

`LynxView` 底层依赖 Lynx SDK，不走浏览器 DOM。

简化流程：

```text
容器拿到 schema
  ↓
解析出 Lynx 资源地址、初始化数据、GlobalProps
  ↓
加载 template.js / Lynx bundle
  ↓
Lynx 引擎 decode 产物
  ↓
主线程构建首屏 UI 树并计算布局
  ↓
创建 LynxUI / 原生 View
  ↓
系统触发 measure / layout / draw
  ↓
页面展示
```

内部资料里对 LynxView 的描述很关键：

> LynxView 本质上是一个原生 Layout，但它的 `measure/layout` 逻辑会被 Lynx 接管，布局结果来自 Lynx 的渲染和排版系统，而不是普通 Android View 自己完成。

LynxView 需要容器提供：

| 输入 | 作用 |
|------|------|
| `template.js` / bundle | 页面模板和前端产物 |
| `TemplateData` | 首屏数据 |
| `GlobalProps` | 设备、主题、实验、业务上下文等全局参数 |
| `LynxViewClient` | 生命周期和加载回调 |
| JSB / Native Module | 前端调用端能力 |

### WebView 和 LynxView 的核心区别

| 对比 | WebView | LynxView |
|------|---------|----------|
| 运行模型 | 浏览器内核 | Lynx 引擎 |
| 页面产物 | HTML / CSS / JS | Lynx bundle / template.js |
| UI 结构 | DOM | Element Tree / Virtual Node / LynxUI |
| 渲染方式 | Web 渲染管线 | Native 渲染或自渲染 |
| JS 依赖 | 页面逻辑和渲染都强依赖 JS / DOM | 首屏可通过主线程和模板直出，业务逻辑在 JS 线程 |
| 端能力 | JSBridge | JSBridge / Native Module |
| 优势 | Web 生态完整、开发成本低 | 首屏和交互性能更强，更适合高性能端内场景 |
| 代价 | 性能受 WebView 和 JS 执行影响 | Web API 不完整，没有浏览器 DOM，学习成本更高 |

### 面试表达

> WebView 和 LynxView 都是 App 内承载前端页面的原生视图。WebView 本质是内嵌浏览器，用来跑 H5；LynxView 是 Lynx SDK 的渲染视图，用来跑 Lynx bundle。业务容器会在它们之上封装 schema 解析、资源加载、JSB、GlobalProps、监控和生命周期，所以容器是更上层的运行环境，WebView / LynxView 是底层渲染承载。

## 4. AnnieX

### 是什么

AnnieX 是字节内部的统一跨端容器。它是在 Bullet、Annie 等多个历史容器能力基础上做融合和治理后的统一容器基座。

可以理解成：

> AnnieX 是字节 App 内承载 H5 / Lynx 跨端页面的统一容器方案。

它不是单纯的渲染引擎，而是一个容器体系：负责页面加载、业务定制、端能力治理、资源加载、监控、安全、性能优化等。

按照前面“容器”的抽象定义，AnnieX 可以被视为容器，是因为它给 H5 / Lynx 页面提供了完整运行环境：

| 容器能力 | AnnieX 中的体现 |
|----------|----------------|
| 承载内容 | 承载 H5 / Lynx 跨端页面 |
| 创建运行环境 | 创建 WebView / LynxView 等底层视图 |
| 屏蔽底层差异 | 统一不同历史容器、不同宿主、不同端能力差异 |
| 提供通用能力 | 路由、资源加载、JSB、GlobalProps、生命周期、监控 |
| 管理运行过程 | 处理加载、渲染、错误、安全、性能优化等链路 |

所以 AnnieX 的“容器”含义不是操作系统级隔离，而是 **客户端页面运行环境封装**。

### 解决什么问题

历史上不同业务线有不同容器，容易出现：

| 问题 | 影响 |
|------|------|
| 容器接口不一致 | 前端要写大量适配代码 |
| JSB 重复建设 | 同类端能力多套实现 |
| 监控口径不一致 | 难以统一评估性能和稳定性 |
| 性能优化重复做 | 每个容器各自建设预取、预加载等能力 |
| 迁移成本高 | 业务换容器需要大量改造 |

AnnieX 解决的是 **容器统一和能力收敛**：

| 方向 | AnnieX 的作用 |
|------|---------------|
| 架构治理 | 统一基础容器 API 和业务定制层 |
| 端能力治理 | JSB 收敛到统一能力体系，如 XBridge |
| 资源治理 | 统一资源加载链路，如 Forest |
| 性能优化 | 提供 Preload、Prefetch、Prerender、极简卡片等能力 |
| 安全合规 | 统一处理 Lynx 验签、JSB 权限、路径穿越等风险 |

### 技术原理

AnnieX 的核心思路是：

```text
统一底座
  ↓
收敛基础能力
  ↓
通过业务定制层扩展差异
```

可以简化为：

```text
业务页面
  ↓
AnnieX 对外 API
  ↓
业务 biz 定制层
  ↓
统一基础容器
  ↓
WebView / LynxView / HybridKit
  ↓
资源加载、JSB、监控、安全、性能优化
```

关键设计：

| 设计 | 作用 |
|------|------|
| 基础容器收敛 | 减少 Bullet、Annie 等多套容器差异 |
| biz 定制层 | 允许直播、电商、财经等业务注入差异逻辑 |
| JSB 融合 | 减少端能力重复建设，统一调用和治理 |
| 资源预加载 | 把资源获取从页面主链路前移 |
| 预渲染 | 提前创建和渲染页面，打开时直接上屏 |

### 面试表达

> AnnieX 是统一容器，它的价值不是让前端换一种语法，而是统一端内跨端页面的运行环境。它把路由、资源加载、JSB、性能优化、安全和监控这些共性能力沉淀到容器层，业务只需要在标准接口上做定制。

## 5. Lynx

### 是什么

Lynx 是字节开源的高性能跨端渲染框架。它让开发者用类似 Web / React 的方式开发页面，但最终在 iOS、Android、HarmonyOS、Web 等平台上以更接近 Native 的方式渲染。

一句话：

> Lynx 是用前端开发体验构建高性能 Native UI 的跨端框架。

### 解决什么问题

传统 H5 / WebView 的优势是开发效率高、动态化强，但性能容易受限于 WebView 和 JS 执行。

React Native 等方案虽然使用 Native 组件，但首屏和更新仍然强依赖 JS 线程。

Lynx 主要解决：

| 问题 | Lynx 的方向 |
|------|-------------|
| 首屏白屏 / 闪烁 | 首屏直出 / Instant First-Frame Rendering |
| JS 阻塞 UI | 双线程模型，UI 渲染与业务逻辑分离 |
| 跨平台一致性 | 统一元素抽象映射到多端 Native 控件 |
| 动态化需求 | 前端 bundle 动态下发 |
| 高性能卡片 / 页面 | 原生渲染或自渲染，减少 WebView 开销 |

### 技术原理

Lynx 的核心是 **编译期前移 + 双线程运行 + 数据驱动渲染**。

```text
前端源码
  ↓
Rspeedy / 构建工具编译
  ↓
生成 Lynx bundle / template.js / 字节码 / 样式
  ↓
客户端 LynxSDK 加载模板和初始数据
  ↓
主线程快速完成首屏渲染
  ↓
后台线程执行业务 JS / ReactLynx 生命周期
  ↓
数据变化驱动 UI 更新
```

关键技术点：

| 技术点 | 作用 |
|--------|------|
| Element Tree | 类似 DOM 的 UI 抽象，但不是浏览器 DOM |
| 双线程模型 | 主线程负责首屏、布局、关键交互；后台线程负责业务逻辑 |
| Lepus / PrimJS | 用于执行模板渲染或主线程脚本的轻量运行时 |
| Starlight | 自研布局引擎，处理排版 |
| ReactLynx | 让开发者用类似 React 的方式写 Lynx 页面 |
| Native Modules / JSB | 连接前端代码与客户端能力 |

### 面试表达

> Lynx 适合对性能要求更高的端内页面或卡片。它和 H5 最大区别是没有浏览器 DOM，而是通过 Lynx 的元素树和 Native 渲染管线渲染。首屏渲染尽量放在主线程快速完成，业务逻辑放在后台线程执行，从而降低 JS 阻塞 UI 的风险。

## 6. 构建工具

### 是什么

构建工具是把开发者写的源代码转换成运行环境能识别、能高效加载的产物的工具。

在前端里，开发代码通常不是浏览器或客户端能直接运行的最终形态，例如：

| 开发时写的内容 | 构建后变成 |
|----------------|------------|
| TypeScript | JavaScript |
| JSX / ReactLynx | 可执行 JS / Lynx bundle |
| Less / Sass | CSS |
| 多文件模块 | 打包后的资源 |
| 图片、字体 | 可部署的静态资源 |

### 解决什么问题

构建工具解决的是：

| 问题 | 构建工具的作用 |
|------|----------------|
| 浏览器或容器不认识 TS / JSX | 转译成目标环境可运行代码 |
| 项目文件很多 | 解析依赖并打包 |
| 资源太大 | 压缩、拆包、Tree Shaking |
| 多环境差异 | 根据环境生成不同产物 |
| 开发效率 | 本地 dev server、热更新、错误提示 |

### 技术原理

构建工具的一般流程：

```text
入口文件
  ↓
解析依赖图
  ↓
加载不同类型资源
  ↓
转译 / 编译
  ↓
代码优化
  ↓
生成产物
```

在 Lynx / PIA 场景下：

| 技术栈 | 构建重点 |
|--------|----------|
| Lynx | 生成 Lynx 可加载的 bundle / template / 样式 / 字节码 |
| PIA | 生成 H5 页面产物、SSR/NSR/Worker 等多类产物 |
| 普通 Web | 生成浏览器可运行的 JS/CSS/HTML 静态资源 |

### 面试表达

> 构建工具本质是把开发态代码转换成运行态产物。在跨端场景里，它不只是压缩打包，还要生成容器能识别的产物，比如 Lynx bundle、PIA Worker、SSR/NSR 产物等。

## 7. PIA

### 是什么

PIA 是字节 Web Infra 团队面向 Mobile Web 的高性能 H5 研发方案。它以普通 H5 应用为基础，通过客户端能力渐进增强页面性能。

可以理解成：

> PIA = H5 应用 + 构建框架 + 运行时 + 客户端 SDK + 性能增强能力。

PIA 主要由：

| 组成 | 作用 |
|------|------|
| PIA Kit | 前端研发框架和构建能力 |
| PIA Runtime | WebView 内的运行时能力 |
| PIA SDK | 客户端侧配套能力 |
| PIA Worker | 不依赖 WebView 提前运行的 Worker |
| PIA Console / Metrics | 调试和质量度量工具 |

### 解决什么问题

普通 H5 页面在端内常见问题：

| 问题 | PIA 的解决方向 |
|------|----------------|
| 首屏慢 | Prefetch、NSR、Snapshot |
| WebView 启动晚 | 通过 PIA Worker 提前执行部分逻辑 |
| 接口等待时间长 | WebView 启动前并行请求数据 |
| 二次进入重复渲染 | Snapshot 缓存页面结构 |
| 端内调试困难 | PIA Console、pia.dev、SPM |

### 技术原理

PIA 的核心思想是 **不推翻 H5，而是在端内逐步增强 H5**。

典型能力：

| 能力 | 原理 |
|------|------|
| Prefetch | WebView 启动前，PIA Worker 提前请求首屏数据 |
| NSR | 在 PIA Worker 中提前执行目标页面渲染逻辑，生成 HTML |
| Snapshot | 缓存页面 DOM / HTML，下次进入时先展示缓存 |
| SSR | 服务端提前生成 HTML，减少客户端首屏等待 |
| PIA Console | 查看端能力、Worker、环境和运行状态 |

简化流程：

```text
用户即将打开页面
  ↓
客户端提前启动 PIA Worker
  ↓
Worker 预请求数据 / 预生成 HTML
  ↓
WebView 创建
  ↓
PIA Runtime 与 Worker 建联
  ↓
页面直接消费预取数据并渲染
```

### 面试表达

> PIA 是 Mobile Web 的性能增强方案，不是替代 H5，而是在 H5 基础上通过客户端 Worker、Runtime 和 SDK 做渐进增强。它常用 Prefetch、NSR、Snapshot 等能力把请求、渲染或缓存前置，减少用户看到首屏前的等待时间。

## 8. Hybrid DevTools

### 是什么

Hybrid DevTools，常简称 HDT，是字节内部用于调试端内跨端页面的工具。它支持 Lynx 和 PIA / H5 场景，提供类似 Chrome DevTools 的调试体验。

它可以理解成：

> 运行在 App 页面和 PC 调试面板之间的远程调试桥梁。

### 解决什么问题

端内页面不像 PC Web 页面一样直接打开浏览器 DevTools。它运行在 App 的 WebView、LynxView 或容器里，调试难点包括：

| 问题 | HDT 提供的能力 |
|------|----------------|
| 看不到页面结构 | 元素审查 |
| 样式问题难定位 | CSS 查看和实时修改 |
| JS 问题难断点 | Sources / 断点调试 |
| JSB 调用不透明 | JSB 记录、Mock、Invoke |
| 接口请求难观察 | 网络抓包 |
| 容器上下文不清楚 | GlobalProps、环境信息 |
| PIA Worker 难调试 | Worker 日志和断点 |

### 技术原理

HDT 的核心原理类似远程 DevTools：

```text
端内页面
  ↓
客户端集成 HDT SDK / 调试能力
  ↓
设备与 PC 通过 WebSocket / USB 等方式建立连接
  ↓
PC 调试面板发送调试命令
  ↓
客户端执行命令并返回页面结构、日志、网络、JSB 等信息
```

公开 Web 调试体系里，Chrome DevTools 和浏览器之间通过 Chrome DevTools Protocol（CDP）通信。HDT 也借鉴了类似思路：把页面检查、网络、Console、断点等能力远程暴露到 PC 调试面板。

### 面试表达

> HDT 是端内跨端页面的调试工具。它解决的是 WebView / LynxView 内页面无法像 PC Web 那样直接调试的问题。它通过客户端调试 SDK 和 PC 面板建立连接，把元素、样式、日志、网络、JSB、GlobalProps 等信息暴露出来，提升联调和问题定位效率。

## 9. Schema

### 是什么

`schema` 在项目里容易有两种含义，需要区分：

| 语境 | 含义 |
|------|------|
| 页面 schema / scheme | 一种用于打开 App 页面或容器页面的 URI 链接 |
| JSON Schema | 对 JSON 数据结构和字段约束的描述 |

在跨端页面开发里，大家常说的“配置页面 schema”，通常指第一种：**页面打开协议**。严格来说，它更接近 `scheme URL` 或 `deep link`，但公司内部常沿用 `schema` 这个叫法。

### 解决什么问题

页面 schema 解决的是：

| 问题 | schema 的作用 |
|------|---------------|
| 如何从外部打开 App 内页面 | 用 URI 表达目标页面 |
| 如何指定容器类型 | host / path / query 中携带容器参数 |
| 如何传递页面参数 | query 携带业务参数 |
| 如何联调不同环境 | schema 中携带本地、BOE、PPE、资源地址等参数 |
| 如何通过二维码打开页面 | 把 schema 转成二维码扫码 |

示例：

```text
snssdk1128://webview?url=https%3A%2F%2Fexample.com%2Fpage
aweme://hunter_lynxview/?channel=xxx&bundle=yyy
```

### 技术原理

移动系统和 App 会注册自己能处理的 URI scheme。

当用户点击或扫码打开 schema 时：

```text
schema 链接
  ↓
系统识别 scheme
  ↓
唤起对应 App
  ↓
App 路由层解析 host/path/query
  ↓
选择容器和页面
  ↓
容器加载 H5 / Lynx 资源
  ↓
页面拿到参数并渲染
```

它和 JSBridge 也有关：早期 H5 调 Native 的一种方式，就是构造特殊 scheme，让 WebView 拦截后交给 Native 处理。

JSON Schema 则是另一类概念：

```text
JSON 数据
  ↓
Schema 描述字段类型、必填项、枚举、范围等
  ↓
平台或程序校验数据是否合法
  ↓
也可用于生成可视化表单
```

例如 TCC 配置里的 Schema 用于约束配置结构，让非研发同学也能按表单编辑配置，避免字段类型和结构错误。

### 面试表达

> 在跨端业务里，schema 通常指打开端内页面的协议链接，本质是一种 URI。它告诉 App 要打开哪个容器、加载哪个资源、携带哪些业务参数。另一个概念是 JSON Schema，用来约束配置或接口数据结构。面试时需要区分这两个语境。

## 10. 这些概念之间的关系

可以用一条端内页面链路串起来：

```text
测试阶段：
泳道负责让请求进入指定后端代码版本

页面入口：
schema 负责描述要打开哪个端内页面

运行环境：
容器 / AnnieX 负责创建 WebView 或 LynxView，注入端能力和上下文

渲染技术：
H5 / PIA / Lynx 负责页面具体实现和渲染

研发构建：
构建工具负责把源码产生成容器能加载的资源

调试定位：
Hybrid DevTools 负责查看页面、日志、网络、JSB 和容器信息
```

## 11. 面试时的表达重点

| 概念 | 面试不要只说 | 应该表达 |
|------|--------------|----------|
| 泳道 | 测试环境 | 流量染色、链路透传、代码隔离、共享数据风险 |
| 容器 | App 里打开页面 | 给某类内容提供运行环境的载体；客户端容器不同于 Docker 容器 |
| WebView / LynxView | 两个页面组件 | App 内承载 H5 / Lynx 的底层原生视图，容器在其上封装通用能力 |
| AnnieX | 一个容器 | App 内跨端页面运行环境封装，统一 H5 / Lynx 的路由、资源、JSB、监控和性能能力 |
| Lynx | 跨端框架 | 高性能 Native UI、双线程、首屏直出、无 DOM |
| 构建工具 | 打包工具 | 开发态到运行态产物转换，生成容器可加载资源 |
| PIA | H5 框架 | 基于 H5 的端内性能增强方案 |
| HDT | 调试工具 | 远程调试端内 WebView / LynxView 的工具链 |
| Schema | 页面链接 | URI 路由协议；另需区分 JSON Schema |
