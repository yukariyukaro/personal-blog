## 2. 现有代码事实

### 2.1 Monitor 是 H5 监控统一入口

`stocks_h5` 的监控能力集中在 `lib/monitor/src/monitor.ts`，页面代码不直接操作底层 Slardar、Metrics 或 Kepler，而是通过 `Monitor` 统一上报。

核心入口包括：

- `Monitor.initMonitor`：初始化 Babus、Slardar、MetricsPlugin、Alog、RRP、TeaRecorder。
- `Monitor.reportPageReady`：页面 ready 上报，底层调用 `babus.pageready()`。
- `Monitor.reportRequest`：请求成功率、错误码、耗时上报，底层调用 `babus.reportRequestStandard()`。
- `Monitor.reportAction`：关键业务动作上报，适用于需要被 Babus/Kepler 监控的业务流程。
- `Monitor.reportActionError`：业务异常上报，适用于失败、降级、不可恢复路径。
- `Monitor.reportEvent`：普通观察事件，不应承载错误、请求、关键动作语义。
- `Monitor.ProcessMonitor`：关键流程耗时打点。

相关代码：

- `lib/monitor/src/monitor.ts`
- `lib/monitor/src/babus.ts`
- `lib/monitor/src/processMonitor.ts`
- `apps/stocks/src/apis/report/index.ts`

### 2.2 Babus MetricsPlugin 已经承担双报职责

当前 `initBabus` 中已经接入：

```ts
babus.use(
  MetricsPlugin({
    psm,
    bizLine: BizLine.XJ,
    pid,
    commonParams: babusParams,
  })
);
```

这说明 Metrics 数据应优先由 Babus 插件统一生成。需求文档也明确提出：后续应避免 `Monitor` 内继续手动调用 `MetricLog.reportEvent` 造成重复上报和指标污染。

这条原则是规范的基础：代码层只维护事件语义，双报链路由 Babus 插件承担。

### 2.3 页面 ready 的现有口径

Babus 文档中 `pageready` 的意思是：页面准备就绪，用户可以开始交互；它不同于 `pageshow`，因为 `pageshow` 不代表页面已正确展示。

项目内已有页面不是在请求开始或骨架屏展示时上报 ready，而是在业务认为首屏核心内容可展示后调用 `Monitor.reportPageReady()`。

典型样例：

- `fundLanding`：`config` 已存在且 `isLoading=false`，页面进入真实内容分支后上报。
- `marketAnomalyLanding`：`status === 'data' && hasCoreContent` 后上报。
- `stockDetail`：`isStockSnapshotReady` 后上报。
- `bindCardLanding` / `etfFirstPurchase` / `limitUpRelatedEtf`：通过 `firstPageReady` 状态收敛 ready 时机。

以 `fundLanding` 为例：

```ts
// 秒开率：列表展示时上报页面就绪
useEffect(() => {
  if (!config || isLoading || hasReportedPageReadyRef.current) return;
  hasReportedPageReadyRef.current = true;
  Monitor.reportPageReady();
}, [config, isLoading]);
```

同时页面在真实内容分支插入 FMP 标记：

```tsx
{isConfigReady && <div className="bfmp" babus-fmp="true"></div>}
```

这说明 ready 和 FMP 都应跟随“首屏核心内容可展示”的业务状态，而不是简单跟随组件挂载。

### 2.4 PIA/FMP 已有基础能力

H5 项目在 `pia.config.ts` 中接入了 `@piajs/plugin-fmp`：

```ts
fmp({
  id: 'root',
  attributeName: 'babus-fmp',
});
```

页面通过隐藏的 `.bfmp` 节点标记业务 FMP，`PageLayout` 统一触发 `reportPIAMetrics()`，采集：

- `getPerformanceMetrics()`
- `getPrefetchRuntimeInfo()`
- `getSnapshotRuntimeInfo()`
- `HTML_START`
- `BABUS_FMP`
- `TOTAL_PREFETCH_LATENCY`

这些数据通过 `Monitor.reportEvent('custom_pia_metrics', piaMetrics)` 和 `Monitor.reportTeaEvent('pia_metrics', ...)` 上报。

这说明页面规范里不需要每个页面重复发明 FMP 采集方式，只需要遵循“首屏真实内容旁放置 `babus-fmp` 标记”的约定。

### 2.5 请求与 prefetch 已有统一上报链路

请求层通过 `apps/stocks/src/apis/report/index.ts` 统一构造请求监控参数：

- `latency`
- `logId`
- `retStatus`
- `retCode`
- `bizCode`
- `eventType: MONITORE_EVENT_TYPE.API`
- `retMessage`

随后调用 `Monitor.reportRequest(url, monitorReportOptions)`。

PIA prefetch 则通过 `apps/stocks/src/apis/report/prefetchMonitor.ts` 读取 `getPrefetchMetrics()`，将 `WRD` 或 `PPE - PPS` 作为耗时，并补充：

- `eventType: MONITORE_EVENT_TYPE.PREFETCH`
- `prefetchHit`
- `prefetchMode`
- `prefetchCode`

因此页面代码不应绕过统一请求入口单独打请求成功率或耗时指标，除非该页面确实存在非标准请求链路。

## 3. Skill 使用方式与沉淀方法

### 3.1 使用 lark-doc 读取需求与 API 依据

我使用 `lark-doc` skill 读取两类文档：

- Babus API 文档，用来确认 SDK 语义。
- 本次需求文档，用来确认改造目标、API 映射方案、指标污染控制和验收标准。

从 Babus 文档得到的关键结论：

- `pageready` 表示页面已正确展示并可交互，不等同于 `pageshow`。
- `reportRequest` 与报警规则关联，请求异常需要传入 `error`，Babus 会按 `[req]` / `[err]` 前缀使用不同报警策略。
- `reportAction` 会自动创建报警规则并被 Babus 监控，不需要告警时不要使用。
- `reportActionError` 用于业务异常流程，会自动创建同比向上波动告警。
- `reportEvent` 只是 Slardar 自定义事件，不应承载请求、异常、关键动作语义。
- `reportTotalActualFMP` 的口径是从客户端开始创建容器到调用后下一次绘制的耗时，仅适用于财经容器中的 Web 场景。

从需求文档得到的关键结论：

- 先改造已有上报 API 和双报链路，不优先新增页面指标。
- Metrics 数据统一由 Babus `MetricsPlugin` 产生，避免 `MetricLog` 手动重复上报。
- 动作、异常、请求、日志要分别映射到 Babus 专用 API。
- 保留 RRP、Alog、TeaRecorder，不扩大成监控体系重写。
- 新增 action/error 前必须证明可告警、可定位、低噪音。

### 3.2 使用 kepler-monitor-setup 提炼监控治理原则

我没有把 `kepler-monitor-setup` 只理解为“创建监控的工具”，而是参考它的工作流提炼代码规范：

- 监控建设应先梳理，再评审，再创建，不应在代码里无差别新增事件。
- 只针对需求新增逻辑或改动点周边梳理监控，不扩大到整个模块。
- 常见监控类型包括 PV、展现成功率、渲染异常率、接口成功率/错误率、列表空推率、点击/转化率。
- 每个监控必须写清楚名称、场景、Metric、Filters、聚合粒度、阈值方向、告警接收人。
- Metric 命名和过滤条件必须参考同项目已有监控，不能跨项目照搬。
- 创建监控后还要验证分组、状态、接收人、阈值和最终服务端配置。

这些原则反推到代码规范里，就是：页面代码只上报有明确监控价值的事件，并且事件名、字段、标签基数要能支撑 Kepler 后续配置和排障。

## 4. H5 页面监控代码规范

### 4.1 页面 ready 规范

页面必须在“首屏核心内容真实可用”后调用 `Monitor.reportPageReady()`。

推荐做法：

- 使用页面业务状态定义 ready 条件，例如 `isConfigReady`、`firstPageReady`、`hasCoreContent`、`isStockSnapshotReady`。
- 使用 `useRef` 做页面内单次保护。
- ready 条件应和真实内容分支一致，不能在骨架屏或 loading 状态上报。
- ready 上报附近应同步放置 `babus-fmp` 标记，保证秒开率与 FMP 口径一致。

不推荐做法：

- 组件 mount 后立即上报。
- 请求发起后立即上报。
- 只要接口返回就上报，但页面还在等待核心数据整理、空态判断或快照恢复。
- 因普通图片、二次跳转链接、非首屏增强能力未完成而无限推迟 ready。

代码模板：

```tsx
const hasReportedPageReadyRef = useRef(false);
const isPageReady = !loading && Boolean(coreData);

useEffect(() => {
  if (!isPageReady || hasReportedPageReadyRef.current) return;
  hasReportedPageReadyRef.current = true;
  Monitor.reportPageReady();
}, [isPageReady]);

return (
  <PageLayout {...pageConfig}>
    {isPageReady && <div className="bfmp" babus-fmp="true" />}
    {isPageReady ? <RealContent /> : <Skeleton />}
  </PageLayout>
);
```

### 4.2 FMP 规范

H5 页面使用 `babus-fmp` 标记业务 FMP。

推荐做法：

- 在首屏核心内容 ready 时渲染 `<div className="bfmp" babus-fmp="true" />`。
- 保持 `.bfmp` 为 1px、透明、绝对定位的隐藏节点，不影响布局。
- 如果页面有多种首屏分支，必须确保成功态、空态或可交互态都能有明确 FMP 标记。
- FMP 标记应靠近业务内容分支，而不是统一放在页面最外层无条件渲染。

不推荐做法：

- loading 或骨架屏阶段渲染 `babus-fmp`。
- 页面所有资源加载完才渲染 FMP，导致指标偏晚。
- 多个互斥分支重复渲染多个 FMP 标记，导致口径不清。

### 4.3 请求监控规范

页面接口必须优先走统一请求封装，复用 `monitorRequest -> Monitor.reportRequest -> babus.reportRequestStandard` 链路。

请求监控必须包含：

- 标准化 URL 或 path。
- `latency`。
- `logId`。
- 业务成功/失败标记。
- `retStatus`、`retCode`、`bizCode`、`retMessage`。
- 必要时补充 `eventType`、`prefetchHit`、`prefetchMode` 等分类字段。

不推荐做法：

- 页面内自行 `Date.now()` 后直接 `Monitor.reportEvent` 上报请求耗时。
- 把业务失败伪装成普通观察事件。
- 为每个接口字段都扩展 Metrics tag，造成标签基数膨胀。

### 4.4 action 与 error 规范

`Monitor.reportAction` 和 `Monitor.reportActionError` 会进入可告警体系，必须谨慎使用。

适合 `reportAction` 的场景：

- 影响核心链路的关键业务动作成功。
- 需要观察趋势并配置告警的成功路径。
- 有明确 owner 和处理预案的业务流程节点。

适合 `reportActionError` 的场景：

- 业务异常、降级、关键能力失败。
- JSB、宿主能力或业务流程返回失败，且不是用户主动取消。
- 能定位问题归因，并可配置同比向上波动告警。

不适合进入 action/error 的场景：

- 普通按钮点击。
- BTM/TEA 已经覆盖的产品分析事件。
- 用户主动关闭、取消、返回。
- 无 owner、无处理手段、无降噪策略的事件。

判断清单：

- 这个事件是否能触发有效告警？
- 告警后谁处理？
- 告警能否定位到页面、接口、场景或业务动作？
- 是否存在低流量、灰度、节假日等噪音？
- 是否可以用已有请求监控、BTM 或 TEA 解决？

### 4.5 reportEvent 规范

`Monitor.reportEvent` 只用于低优先级观察事件或兼容旧调用。

可以使用：

- 临时诊断。
- 不触发告警的状态观察。
- 需要进入 Slardar 自定义事件但不应进入 action/error 体系的事件。

禁止使用：

- 网络请求成功率、耗时、错误。
- 业务关键动作。
- 业务异常。
- 产品点击曝光分析。

如果事件未来要接 Kepler 告警，应先迁移为 `reportAction` 或 `reportActionError`，而不是继续扩展 `reportEvent`。

### 4.6 PIA 指标规范

PIA 指标由 `PageLayout` 统一触发 `reportPIAMetrics()`，页面侧无需重复采集。

页面需要做的是：

- 使用项目统一 `PageLayout`。
- 按业务 ready 条件放置 `babus-fmp`。
- 对 SSR、prefetch、snapshot 页面确认 ready 条件不早于真实内容恢复。
- 对异常降级页面明确是否应上报 ready、FMP、error。

对资源加载异常，`pia.config.ts` 已通过 `assetsRetry` 上报：

- `pia_assets_retry`
- `pia_assets_retry_success`
- `pia_assets_retry_fail`

页面内不应重复造一套资源重试监控，除非有页面专属资源链路。

## 5. 从代码到 Kepler 监控的工作流

### 5.1 梳理阶段

每次新增页面或关键链路时，先按以下顺序梳理：

1. 读需求文档，只针对新增逻辑和改动点梳理，不扩大到整个模块。
2. 读页面现有代码，找出 ready、FMP、请求、业务动作、异常、空态、降级路径。
3. 读同项目已有监控或已有上报代码，确认事件名和字段口径。
4. 判断哪些事件已经被统一请求监控、PIA 指标、BTM、TEA 覆盖。
5. 只为未覆盖且具备告警价值的路径设计 action/error。

### 5.2 方案阶段

每个候选监控必须写清楚：

| 字段 | 说明 |
| --- | --- |
| 监控名称 | 遵循项目已有命名风格 |
| 场景 | 为什么需要这个监控 |
| 上报 API | `reportPageReady` / `reportRequest` / `reportAction` / `reportActionError` / `reportEvent` |
| 事件名 | 业务可读、稳定、可检索 |
| categories | 低基数、可定位，不塞大对象 |
| metrics | 仅保留必要耗时或数值 |
| Kepler 类型 | PV、成功率、异常率、空推率、转化率等 |
| 阈值方向 | 上升告警或下降告警 |
| owner | 告警接收与处理人 |

### 5.3 代码阶段

代码实现按以下优先级：

1. 优先复用 `Monitor` 统一入口。
2. 优先复用请求层统一上报。
3. 页面 ready 和 FMP 绑定业务首屏状态。
4. action/error 只覆盖高价值路径。
5. 事件字段只使用稳定、低基数、可定位的 tags。
6. 不在页面中直接依赖 `@fe/metrics-web` 或手写 Metrics 上报。

### 5.4 Kepler 阶段

参考 `kepler-monitor-setup` 的流程，监控创建不应跳过评审和验证：

1. 先输出监控梳理结果给业务或 owner 评审。
2. 确认 project_id、token、region、分组、阈值、告警接收人。
3. 创建时优先抄同项目已有监控模板，不跨项目套用 Metric 命名。
4. 创建后执行 `create -> batchchoosemonitorgroup -> updatemonitorstatus -> getmonitordetail`。
5. 回填最终 MonitorId、分组、状态、阈值、接收人和子任务生成情况。

## 6. 指标污染控制

这次需求最重要的约束是控制指标污染。

容易造成污染的行为：

- `Babus MetricsPlugin` 已经双报后，又在 `Monitor` 内手动 `MetricLog.reportEvent`。
- 每个点击都上报 `reportAction`。
- 把用户取消、关闭、返回当成异常。
- 把高基数字段放入 categories，例如完整 URL、JSON、股票列表、错误堆栈。
- 为了“覆盖全面”新增没有 owner 的告警事件。
- 页面内绕过统一请求上报，重复打接口成功率。

推荐控制方式：

- `reportPageReady` 只报一次。
- `babus-fmp` 只在首屏核心内容可用时出现。
- 请求监控统一走 `reportRequest`。
- 业务动作和业务异常分开上报。
- 普通产品分析继续走 BTM/TEA。
- Kepler 只接入有告警价值、可定位、低噪音的事件。

## 7. 页面接入检查清单

新增或改造 H5 页面时，我会按下面清单检查：

- [ ] 页面是否使用统一 `PageLayout`。
- [ ] 页面是否定义了明确的 ready 条件。
- [ ] `Monitor.reportPageReady()` 是否只在真实内容可用后调用一次。
- [ ] 页面是否在同一 ready 条件下渲染 `babus-fmp` 标记。
- [ ] 首屏成功态、空态、降级态是否都明确了 ready/FMP 策略。
- [ ] 页面接口是否走统一请求封装。
- [ ] 请求失败是否能通过 `reportRequest` 带出 `retCode`、`retMessage`、`logId`、`latency`。
- [ ] 是否有真正需要 `reportAction` 的关键动作。
- [ ] 是否有真正需要 `reportActionError` 的业务异常。
- [ ] 普通点击、曝光、产品分析是否继续走 BTM/TEA，而不是 action/error。
- [ ] categories 是否低基数、稳定、可定位。
- [ ] 是否避免页面内直接依赖 `@fe/metrics-web`。
- [ ] Kepler 监控方案是否经过 owner 确认。

## 8. 本次需求的产出价值

这次需求不是简单地给某个页面补几个埋点，而是把 `stocks_h5` 的页面监控沉淀成一套可复用规范。它的价值可以从稳定性、效率、质量和协作四个维度展示。

### 8.1 稳定性价值

- 明确 `page_ready` 与 `babus-fmp` 的上报时机，让秒开率、FMP 等性能指标更贴近用户真实可用时间。
- 统一请求监控入口，保证接口成功率、业务错误码、耗时、logId 等字段一致，便于 Kepler/Slardar 查询和问题定位。
- 区分 `reportAction` 与 `reportActionError`，让关键动作和业务异常进入正确的告警策略，避免普通观察事件误触发告警。

### 8.2 工程效率价值

- 新页面接入监控时不再从零判断 API 选型，可以直接按本文档检查清单完成 ready、FMP、请求、action/error 的接入。
- 监控方案评审不再停留在“要不要加埋点”，而是可以围绕事件语义、告警价值、字段基数、owner 和阈值进行结构化评审。
- Kepler 监控创建前的方案字段被标准化，减少开发、测试、稳定性平台之间的反复沟通。

### 8.3 质量治理价值

- 避免 `Babus MetricsPlugin` 已双报后继续手动 `MetricLog.reportEvent`，降低重复指标和口径冲突风险。
- 控制高基数 categories，避免股票列表、完整 URL、错误堆栈等字段进入 Metrics tags，降低查询成本和告警噪音。
- 保留 BTM/TEA 与 Babus/Kepler 的边界：产品分析继续走 BTM/TEA，稳定性告警走 Babus/Kepler。

### 8.4 协作与复用价值

- 文档把本地代码、官方文档和 Kepler skill 工作流串成一个统一说明，降低后续同学理解成本。
- 后续页面需求可以复用同一套模板：先确认 ready/FMP，再确认请求监控，再判断是否需要 action/error，最后进入 Kepler 方案评审。
- 答辩中可以把它展示为“我把一次页面监控需求沉淀成团队级规范”的案例，而不是一次性脚本或单页面改动。

### 9.2 建议优先补齐的答辩数据

- Kepler 统计：按页面或事件名查询告警数、有效处理数、误报数、平均响应时间。
- 研发流程统计：记录新页面按规范接入监控所需时间，作为后续页面的效率对比基线。
