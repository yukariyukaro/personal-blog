## Q1 你做的项目的亮点？

**90 秒口播主线**

> 「这个项目是抖音理财阵地的一条内容转化链路：行情异动发生后，AI 自动生产一篇热点解读，通过首页卡片推给用户，点进 H5 承接页看事件说明、事件解析、相关 ETF 和基金、指数走势，再决定订阅播报或者直接买入。我负责 H5 承接页和首页异动卡片。
>
> 它的亮点不是『做了一个承接页』，而是三个非功能问题：
 >
> 第一，**SSR 引入后多了一类新 bug：首轮渲染决策依赖了只在客户端才有的取值时机**。开户底栏要用 Portal 挂到 `document.body`、分享入口要靠客户端的 `commonParams.aid` 去取目标短链，这些服务端都不具备。危险的地方在于它不一定表现为水合报错——更常见的是服务端和客户端首轮都走了空分支，两边结构一致、控制台干干净净，但功能就再也不会出现了（我们的分享入口就是这么丢的）。约束是：**首轮结构不能依赖取值时机**，用 effect 里设置的『已挂载』状态量当信号，第二轮再切换。
>
> 第二，**『数据缺失』不等于『不展示』**。指数信息要串行调一个耗时接口才能拿到，我把这个模块拆成三态：只有后端明确标记不展示才隐藏；描述符缺失按未知处理，保留骨架并退避重取，直到拿到明确结论。否则『还没算出来』会被永久当成『不需要展示』。
>
> 第三，**首屏优化做到底，并且算清了天花板**。SSR 加订阅弹窗懒加载，1 秒秒开率从 10% 提到约 75%；然后拆首包发现页面独占资源只占 7%，最大一块 174.9 KB 全是监控和埋点基座 SDK——**单页优化已经到顶了，继续要跨团队动基座**。」

**三条亮点对应的可追问点**

| 亮点 | 会被追什么 | 素材位置 |
|---|---|---|
| SSR 首轮渲染一致性 | 哪两处、为什么共用同一个状态量、「结构一致」为什么不等于正确、不靠约定还能怎么防 | [技术实现概要](../../../../../字节财经-项目经历/异动热点技术实现-restored/17579d71750c713d.md) 水合一致性节 |
| 指数三态与恢复 | 三态怎么分、为什么退避、窄更新的原因 | 同上，补齐节 + 母档 4.3 |
| 首屏优化与天花板 | 秒开率口径、体积数字为什么两个一起给 | [今日异动页性能优化](../../../性能优化/今日异动.md) |

## Q2 怎么优化首屏加载时间？怎么记录的？

### 2.1 优化做了什么

| 手段 | 压哪一段 | 结果 |
|---|---|---|
| PIA SSR（`string-stream`）首屏直出 | 加载延迟（首屏接口往返整段消失） | 与懒加载合计：秒开率 10% → 约 75% |
| 订阅弹窗体系 `React.lazy` + 条件挂载 | 加载时间 | 页面自有首屏 JS 28.4 → 19.5 KB gzip（−31%），首包 517.7 → 504.1 KB（−2.6%） |
| 两层成功判定（业务码 + 内容就绪） | 体验（不是速度） | 避免用户停在"更快的空壳"上，且不阻断恢复链路 |
| CSR 静默恢复 | 体验 | 降级时不清空骨架，避免闪烁 |

**验证方式的硬度**：懒加载不看构建分析图，而是构建后检查该异步 chunk 在页面产物中的引用次数为 0——它直接回答"首屏会不会加载它"。

### 2.2 怎么记录的：走统一监控，不自己打点

**核心原则**：H5 跑在端内容器里，起点在容器初始化和 HTML 下载之前，`Date.now()` 拿不到起点，算出来的既不是首屏也不是渲染耗时。所以全部走项目已有的统一入口。

| 想知道 | 口径 | 来源 |
|---|---|---|
| 秒开率 | `Monitor.reportPageReady()` 的时机 | Babus `pageready`，页面在 `status === 'data' && hasCoreContent` 后上报 |
| FMP | `.bfmp` 隐藏节点 + `babus-fmp="true"` | `pia.config.ts` 的 `@piajs/plugin-fmp` |
| 预取命中与耗时 | `getPrefetchMetrics()`（耗时取 `WRD` / `PPE - PPS`） | `prefetchMonitor.ts` |
| PIA 链路整体 | `HTML_START` / `BABUS_FMP` / `TOTAL_PREFETCH_LATENCY` / prefetch、snapshot 运行时信息 | `PageLayout` 统一 `reportPIAMetrics()` |
| 接口耗时与成功率 | `latency` + `retCode` / `logId` | `Monitor.reportRequest` |
| 资源重试 | `pia_assets_retry` 系列 | `assetsRetry` |

**一个要说清的设计**：ready 的判定条件是"业务码成功 **且** 标题、摘要非空"，不是"接口返回成功"。因为内容是自动生产的，存在 200 但内容还没生成的中间态——按业务码报 ready，秒开率会被空壳页面刷得很好看，但用户看到的就是个空架子。**指标口径、渲染分支、恢复策略三者同源**。

**分析工具（找瓶颈，不是回收数据）**：lighthouse + hybrid devtools 拆各阶段耗时（webview 初始化、资源加载、TTFB、渲染），构建产物报告 + sourcemap 拆包定位体积构成——两套同期并行，互相验证。

### 2.3 追问：小程序里记录加载的起止时间？

起止点选错是这类问题最常见的失分点：

| | 起点 | 止点 |
|---|---|---|
| 标准口径 | 冷启动 `appLaunch`（**不含**客户端运行环境准备与小程序信息准备，这两段微信控制、拿不到） | 首个页面 `Page.onReady` |
| 官方 Performance API | `wx.getPerformance()` 的 `appLaunch` | `firstRender`（首次渲染） |
| 自定义口径 | `Page.onLoad` 记 `t0` | 首屏数据 `setData` 的回调 —— 官方定义就是"setData 引起的界面更新渲染完毕"，**不需要再套 `wx.nextTick`** |

几个容易踩的点：
- **阶段类取 `duration`，时间点类取 `startTime`**：`appLaunch` / `evaluateScript` / `firstRender` 有 `duration`；FP / FCP / LCP 只有时间点，没有 `duration`；
- **FCP / LCP 用 `getEntriesByName(name, entryType)` 取，两个参数都得传**，LCP 要取**最后一条**（更大的内容出现会不断追加条目）；
- **`observe` 没有 Web 的 `buffered`**，观察者必须尽早注册，默认缓冲区只有 30 条；
- **平台支持差异**：FP、LCP 在 iOS 上不支持，FCP 在 iOS 14.5 以下不支持，用前先看 `supportedEntryTypes`；
- **业务接口耗时官方覆盖不到**（`resourceTiming` 只采视图层资源），要用 `wx.request` 回调里的 `profile` 拆 DNS / TCP / TLS / TTFB。

> ⚠️ 上面这套是原生小程序（微信）的口径。异动热点这一侧是 **Lynx 卡片**，对应的采集 API 与钩子 **待确认**——面试前必须自己核一遍，否则这一段只能讲成"设计思路"。
> 完整版见 [tripleuni.md](../../../性能优化/tripleuni.md) 第一章。

### 2.4 追问：Web 端怎么获取首屏加载时间？起止怎么确认？

- **加载阶段**：`PerformanceNavigationTiming` —— `navigationStart` → `domContentLoadedEventEnd` / `loadEventEnd`，逐段可拆 DNS / TCP / TLS / TTFB / 响应；
- **绘制指标**：`performance.getEntriesByType('paint')` 取 FP / FCP；LCP 用 `PerformanceObserver` 订阅 `largest-contentful-paint`；
- **端内 H5 的额外一段**：容器侧（webview 创建、资源/离线包加载、JSB 注入）在浏览器环境下根本量不到，只有 hybrid devtools 能看到；起点若从 `navigationStart` 算，会低估容器那一段；
- **止点不是 load**：性能指标要看"关键内容可见/可用"。本页的止点就是 `status === 'data' && hasCoreContent`（与 FMP 标记同一条件），而不是整页资源加载完；
- **业务接口单独拆**：用 Resource Timing 按 `initiatorType` 过滤出 `fetch` / `xmlhttprequest`，这段和服务端处理耗时可用 `Server-Timing` 拆开；
- **口径提醒**：lighthouse 是实验室数据，线上要看真实用户分位；Web 端 Core Web Vitals 官方看 P75，小程序侧常看 P90，两端不能混。

## Q3 实习团队的主要业务？印象最深的 bug？

### 3.1 团队业务

> 「我所在的团队做抖音理财阵地，也就是财经里的股票、基金、ETF 方向，负责从内容到交易转化的整条链路。上游是内容生产与管理后台，负责行情异动的自动选题、AI 生产和人工审核；中游是抖音小程序侧的入口——首页卡片、行情 tab、站内信，负责把用户带到内容；下游是 H5 承接页，用户在这里看解读、看相关 ETF 和基金，完成自选、订阅和开户买入。
>
> 这几个环节在三个独立仓库，各自有负责人。我负责的是 H5 承接页，以及小程序侧的首页异动卡片和文章咨询页。」

### 3.2 印象最深的 bug

bug 主要集中在 SSR 改造后的回归验证阶段。这个 bug 出现在 SSR 上线之后：测试环境当期要回归验证的功能太多，分享这条链路没被覆盖到，所以自测和测试都没发现，是上线后才暴露的。

> **现象：一部分用户看不到分享入口。** 页面其它部分都正常，控制台没有报错、也没有水合警告——是按钮根本没有渲染出来，不是"点了没反应"。这类"少了东西但不报错"的问题，自测和回归都很难发现。
>
> **根因：拿不到 `aid` 时，分享入口就不渲染。** 分享目标短链要靠客户端的 `commonParams.aid` 来取，服务端没有这个参数，所以服务端首轮渲染时，这一块必然走"不渲染"分支。如果客户端首轮也还没取到 `aid`（取决于容器注入时机），那两边结构就是一致的——**React 不会报任何水合错误**。而 `aid` 就绪之后，没有任何状态变化驱动重新渲染，于是**分享入口永远不出现**。
>
> **关键认识：「结构一致」不等于「正确」。** 以前我以为 SSR 的风险只有水合报错、事件绑定丢失，实际更隐蔽的一类是：服务端和客户端首轮都渲染了空分支，两边谁都报错，功能静默消失。水合不匹配至少还有报错可查，这一类连报错都没有。
>
> **修法：把「渲染结构」和「取值时机」解耦。** 不再让"有没有 aid"参与首轮渲染决策，而是用一个 effect 里设置的「已挂载」信号作为门（和开户底栏共用同一个状态量）：首轮服务端和客户端都不渲染分享入口，挂载完成后第二轮才插入 Header。这样 aid 什么时候就绪都不影响首轮结构，也不会再出现"入口永远不出现"。
>
> **表述上要避免一个说法**：容易把修法说成"把分享按钮挪到客户端渲染"。那样听起来仍是"按环境决定首轮结构"的老路，服务端和客户端首轮依旧可能不一致。准确的说法是「首轮两边都不渲染，挂载后再插入」。
>
> 开户底栏是同一类约束的另一个案例：它要用 Portal 挂到 `document.body`，服务端没有 `document`。

**备选 bug（业务影响面更大）**：接口返回 200 但核心内容字段还没生成，页面按成功进了数据态，用户看到有骨架没内容的壳；更糟的是**已进数据态后客户端的恢复逻辑不会再跑**，页面就永远停在空壳上。修法是在业务码之外追加"标题与摘要非空"的判断（两层成功判定），让这种情况走和 SSR 降级同一条恢复链路。代价是判断标准硬编码在前端，后端改字段语义时要同步改。

## Q4 做过的项目的难点

按"难在哪 → 为什么常规写法不行 → 我怎么解 → 代价"四段讲，挑两个展开就够。

**难点 1：缺失 ≠ 不展示（指数三态 + 退避恢复）**
指数信息不在主接口首屏数据里，要根据主接口返回的指数编码再串行调一个耗时接口。如果把"没拿到"当成"不展示"，这个模块会永久消失。拆成 `hidden / ready / unknown` 之后，未知态有了自己的处理路径：保留骨架，并以 1 秒起、乘 2、上限 30 秒的退避持续重取主接口。
**代价**：退避没有次数上限，某条内容永远不关联指数时会一直重试到页面关闭。

**难点 2：两条进入路径，一套补齐逻辑**
SSR 成功走预置状态、SSR 降级走客户端恢复，两条路径下组件挂载时机不同。补齐逻辑如果散在各组件里，很容易写出"只在其中一条路径下生效"的分支——而且本地开发（SSR 正常）根本不会暴露。所以自选状态、基金跳转配置、指数恢复、指数行情四类补齐都收在同一个 hook，统一以数据态为触发条件。

**难点 3：并行写入源下的窄更新与竞态防护**
指数恢复打的是完整主接口，但落库只合并指数段——整体覆盖会打掉并行补齐的自选状态和基金 schema，用户可见地"自选变回去了"，这是并行写入场景下的必然冲突，不是概率问题。另外补齐结果落库前要重新读状态、重算并比对补齐标识，丢弃期间主数据已变更的过期结果。

**难点 4：自研简易趋势图组件（指数模块）**
指数卡里要画一条当日走势线，本质是**缩减版分时图**。现成的图表库卖点都在交互与实时——Lightweight Charts（35 KB）、ECharts、HQChart 提供的是十字光标、缩放拖拽、指标叠加、流式更新，这个场景一条都不需要；而这一页正在压首包体积，为一条线引入整库是反方向的。
做法是让 AI 参考 Lightweight Charts 的设计生成初版，最终是一个**独立的小组件**：砍掉交互与实时能力，时间刻度只保留当日开盘与收盘。难点不在画线，在坐标口径——
1. **时间轴不能等距映射**。一天是 9:30–11:30 + 13:00–15:00，中间夹 90 分钟午休；按真实时间戳线性映射会把午休压成一段，上午下午的斜率失真。所以按交易时段分段、段内均匀映射。
2. **Y 轴以昨收为对称基准**。分时图看涨跌幅，涨 1% 和跌 1% 要距中线等距，范围取 `±max(|最高−昨收|, |昨收−最低|)`，不能直接用当日 min/max 归一化。
3. **退化输入是常态**：当前时刻之后没有点、停牌是一条平线、只有 1 个点、所有点相等（`min == max` 会除零）。线只画到最后一个有效点，不补零、不补前值。
4. **SSR 下不能用容器宽度算坐标**，否则又回到 3.2 那类"首轮结构依赖取值时机"的问题。
参考 Lightweight Charts 的具体一点：它把"时间 → 刻度语义"和"标签渲染"分两步——内部先给每个时间点推断 `TickMarkType`（年 / 月 / 日 / 时分 / 时分秒），再交给 `tickMarkFormatter` 出标签，并用 `uniformDistribution` 保证同权重的刻度要么都画、要么都不画。我借这个分层，刻度本身收敛成开盘 / 收盘两个。
**降级链路和三态同源**：指数行情是两步，先 `QueryStockSnapshot` 再 `QueryMiniStockTrend`；快照失败不渲染指数卡，趋势失败降级成"没有趋势图"的卡，不画默认线、不补零值。
**AI 协作的边界**：AI 生成的初版在正常数据下能跑，但坐标口径、退化点集、SSR 尺寸这些边界要自己收口。讲"用 AI 编程"时我更愿意举这个例子——不是让 AI 写完，是我定输入契约、砍需求、兜边界。
**代价**：没有十字光标、缩放与指标叠加；后续要加交互得重新评估是否引入图表库。

**可以主动交底的边界（加分，但别主动往深带）**
- hooks 层没有自动化覆盖：现有 6 个契约脚本只对纯函数断言、不跑 effect，所以退避调度、竞态防护、清理函数实际没被测试覆盖；E2E 有 7 个 case 覆盖主路径（SSR 失败后 CSR 恢复、SSR 成功后分享入口水合、水合后补拉指数行情），但要拉浏览器和 Mock，不是每次改动都跑。
- 已识别未落地：补齐失败只打 console、线上不可见；CSR 恢复没有超时兜底。

## 需要自己确认的四件事

1. **`mp_stocks` 侧 Lynx 卡片的首屏采集 API 与起止钩子** —— Q2 追问的落点，也是"两端我都做了"能否讲实的依据。
2. **秒开率 10% → 75% 的落库口径与数据来源**（page_ready / FMP / LCP，线上分位 / HDT 采样 / A/B 组）—— 见[性能稿附录](../../../性能优化/今日异动.md#附需要确认的事实)。
3. **卡片侧有没有独立的难点可讲**（首屏数据竞态、频控去重、卡片转场）—— 目前答案主线都在 H5 承接页，卡片只作为归属出现。
4. **趋势图组件的坐标实现**：渲染用 SVG 还是 Canvas、Y 轴是否真以昨收为对称基准、退化输入（单点 / 全等值）实际怎么处理、刻度是不是就开盘收盘两个 —— 难点 4 我按分时图的通用口径写了，这几条要对着代码核一遍再讲。
