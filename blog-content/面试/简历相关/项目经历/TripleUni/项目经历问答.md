## 一、亮点：一次为 AI 初版代码做的性能 code review

### 1.0 一句话版本

**首页功能跑通之后，我发现 AI 生成的初版代码在体验和性能上是「能用但不耐看」。于是我做了一轮 code review，把三个具体的体感问题定位成三条技术原因，再逐条优化——首屏慢是图片没走缓存，快滑看到骨架屏是预加载触发太晚，滑久了卡顿是列表节点在无限增长。**

这个项目的亮点不在"我写了多少功能"，而在**我能看出 AI 产出的代码哪里不对，并且知道怎么改**。

### 1.1 现象一：首屏渲染时间长

**根因**：初版把所有图片都当成「实时数据」处理——每次冷启动都要重新拉一遍开屏广告和海报，且图片本身没有走 CDN，体积大、节点远。首屏要等这些大文件下载完才敢撤开屏，加上列表接口串行在后，首屏被图片下载吃掉了大量时间。

**优化**：CDN + imageCache 两级缓存，并且**命中本地缓存后跳过对应接口请求**。

1. **资源上 CDN**：把开屏广告、海报等非本地图片统一走 CDN 域名，冷启动时从就近边缘节点取，降低首字节时间。
2. **本地文件缓存**：用 `wx.getFileSystemManager().saveFile` 把图片持久化到本地，缓存键值存成 `{ localPath, src }`——`src` 是这次缓存对应的后端资源 URL。
3. **命中即跳过接口**：启动时先读本地缓存记录，版本没过期就直接用本地文件渲染，**不再发起 `/info/banner`、`/info/openad` 这类图片资源请求**。图片资源的请求直接消失，首屏少了一整轮 RTT。
4. **失效与兜底**：后端换图后 URL 变化，本地 `src` 比对不通过就重新请求并重下；再用 `access` 校验本地文件是否被系统回收，文件不在了同样降级回接口请求。

**这一步的关键认识**：缓存的价值不只是"省一次下载"，而是**能把接口请求整段跳过**。前提是本地必须存一个可比较的版本标识（URL 里的版本号或内容 hash），否则就会一直读到旧图。

### 1.2 现象二：滑动很快的时候，下方的帖子是骨架屏

**根因**：初版是"滚到底才开始请求下一页"，请求的 RTT 期间用户已经滚到空白区域，于是看到骨架屏。这不是渲染问题，是**预加载时机**问题——数据就绪时间落后于用户滚动速度。

**优化**：预加载 + 后端分页。

1. **后端分页**：接口按 `page` 返回，单页控制在约 20 条，首屏 payload 不再随数据量增长。
2. **阈值预加载**：不等滚到底，在**距离底部还有一段距离时**就发起下一页请求，让数据在用户滚到之前就绪。快照里的阈值是 `scrollHeight - scrollTop < 3000`（约一屏半）。
3. **防重入与终止**：用 `is_loading_more` 锁住并发，用 `is_last` 终止到底后的无意义请求，避免快速滚动时连发重复请求。
4. **骨架屏收敛**：骨架屏只在"真正的首屏空窗"出现，不再作为翻页常态。

**这一步的关键认识**：分页解决的是"单次传输量"，预加载解决的是"用户滚到之前数据有没有到"。**只做分页不做预加载，快滑一样会看到骨架屏。**

### 1.3 现象三：滑动久了之后卡顿

**根因**：初版用 `wx:for` 全量渲染整个列表，分页又是不断 `concat` 追加——**滚动越久，真实渲染的节点数线性增长**，每次 `setData` 的 diff 范围和样式重算成本随之上升，几百条之后滚动明显掉帧。

**优化**：改用微信官方推荐的长列表组件，只渲染可视区，滚出去的节点回收复用。

1. **可视区渲染**：列表组件负责计算当前可视区间，只挂载区间内的帖子卡片，上下用撑高的占位块维持滚动条长度。
2. **节点回收复用**：滚出可视区的卡片被回收后再复用到新进入的卡片上，**DOM 数量与列表长度解耦**，从"O(列表长度)"变成"O(可视区)"。
3. **复用正确性**：复用单元的 key 必须用稳定的业务 ID（帖子 ID），不能用 `index`，否则复用错位会把上一个卡片的内容显示到新位置。
4. **图片配合**：卡片进入可视区才触发图片加载，移出后保留占位，避免滚动过程中反复请求造成抖动。

**这一步的关键认识**：长列表的性能瓶颈不是"数据多"，而是"**挂载的节点多**"。虚拟化的本质是把「数据长度」和「渲染节点数」解耦。

### 1.4 三条追问防线

| 会被问 | 怎么答 |
|---|---|
| 你怎么知道缓存过期了？ | 本地存了资源 URL 作为版本标识，URL 变了就是过期。低频变化的资源才允许跳过接口，列表这类实时数据不跳 |
| 阈值 3000 怎么定的？ | 按"一屏高度 + 网络 RTT 对应的滚动距离"估。太大浪费流量，太小来不及，这个值是压测后调的 |
| 快速滚动连续触发怎么办？ | `is_loading_more` 锁住并发请求，`is_last` 终止到底后的请求，保证同一时刻只有一个分页请求在飞 |
| 滚动速度极快，预加载也追不上怎么办？ | 这种极端场景下骨架屏是合理兜底——宁可让用户看到占位，也不要白屏或卡住主线程 |
| 长列表组件的高度怎么处理？ | 定高最稳；不定高要先测量建高度缓存再算区间。这块是组件本身的主要约束 |
| 用了 index 做 key 会怎样？ | 复用错位，节点被回收后复用到新位置时会带上旧内容，表现为卡片内容闪烁或串位 |

> ⚠️ **"微信官方推荐的长列表组件"需要确认具体是哪一个**，因为两者的追问方向完全不同：
> - **`recycle-view`**（微信官方开源的长列表组件）：WebView 渲染下可用，用"屏数 × 每屏条数"维护可视区并提供回收上下文，追问会落在高度测量与回收配置上；
> - **Skyline 的 `list-view`**（`<scroll-view type="list">` + `<list-view>` + `<list-item>`）：回收由 Skyline 渲染引擎负责，需要项目开启 Skyline，追问会落在开启条件、兼容降级和平台差异上。
>

## 二、做项目时有什么难点？

### 2.1 难点一：AI 产出的代码「功能对、体验不对」，怎么把它识别出来

这是这个项目里最本质的难点。AI 生成代码的默认目标是"功能跑通"——接口调通了、数据渲染出来了，它就认为任务完成了。但**首屏关键路径有多长、列表规模会增长到什么量级、预加载该在什么时机触发，这些它默认不会主动考虑**。

我建立的做法是：功能跑通之后，必须补一轮**体验走查**，而不是直接交付。走查方式是三条——

1. 真机走查，不看模拟器，因为滚动掉帧这类问题只有真机能复现；
2. 看性能面板的首屏分段耗时，确认时间花在"资源下载"还是"接口等待"上；
3. 长列表压测，连续滚动到几百条，看掉帧出现在什么位置。

**更重要的沉淀**：把 review 出来的问题反向补进给 AI 的约束里，形成可复用的规则——长列表必须虚拟化、图片必须走缓存并做版本校验、分页必须带预加载阈值、复用 key 必须用业务 ID。这样下一次生成就不会再犯同样的错。

> 这一段和简历里「探索 openspec、个人 skills 等 harness engineering 实践」是同一件事的两面，可以互相印证着讲。

### 2.2 难点二：预加载时机是"请求 RTT"与"用户滚动速度"的赛跑

骨架屏问题的难点不在实现，而在**阈值取舍**：阈值太保守，快滑还是会看到骨架；阈值太激进，用户慢慢看的时候会白白拉一堆用不上的数据，浪费流量也增加服务端压力。

而且快速滚动会连续触发滚动事件，如果不在请求层做防重入，会出现同一个 `page` 被重复请求、回来的顺序还可能错乱。所以最终是"阈值 + 请求锁 + 终止标记"三件套一起上才稳。

### 2.3 难点三：缓存和「后端上了新素材」的冲突

缓存最容易踩的坑是**用户一直看到旧图**——后端换了新海报，但本地缓存还命中，前端就永远显示旧的。

初版的思路是"按 key 缓存"，key 不变就永远命中，这个问题无解。后来改成**把源 URL 一起存进缓存记录**：URL 里带版本或 hash，后端换图 URL 就变，本地比对不通过，缓存自动失效并重新下载。等于用资源地址本身当版本号。

### 2.4 难点四：长列表的「复用正确性」

虚拟化之后，节点是复用的，这带来一个很容易忽略的问题：**复用单元的 key 如果不稳定，节点被回收再复用到新位置时，会带着上一个卡片的内容出现**，表现为滚动时卡片闪一下或内容串位。所以 key 必须用帖子 ID 这类稳定业务标识，不能用 `index`。这类问题不会报错，只会"看起来有点怪"，排查成本很高。

### 2.5 ⬜ 难点五：工程化实现——埋点与监控（设计态）

> **先说边界**：项目当前**没有埋点与监控**——前端全文没有任何上报调用，`IntersectionObserver` 一次都没用过；[info.js](../../../../../tripleuni-frontend-wechat/utils/info.js#L80) 里那个 `report2023.tripleuni.com` 是**被注释掉的独立上报域名**，说明这套基础设施规划过但没启用。
> 所以这一节讲的是**方案**。面试时按「如果我来做，我会这么设计」的口径讲，别讲成已上线。

#### 为什么这也是难点

埋点难在它不是「加个接口」，而是三件事必须同时对：

1. **口径要先定义**，否则数据出来没人敢用；
2. **不能影响主流程**——埋点自己不能成为首屏瓶颈；
3. **埋点自身要可观测**，否则它坏了没人知道，这是最典型的**沉默故障**。

#### 锚点案例：要把「帖子浏览量」显示在前端，怎么做？

**第一步不是写代码，是定义口径。**「浏览量」是个模糊词，至少能拆成四个完全不同的指标：

| 口径 | 定义 | 谁能采 |
|---|---|---|
| 曝光 PV | 卡片进入可视区且满足时长阈值的**次数** | 前端埋点 |
| 曝光 UV | 同一用户在同一时间窗口内**只算一次** | 前端埋点 + 后端去重 |
| 详情进入 PV | 详情页被打开的次数（≈ `/post/single/get` 的调用量） | 前端埋点 或 后端 |
| 阅读完成 | 详情页停留 ≥ N 秒 / 滚到底 | 前端埋点 |

**关键判断：详情页的量后端能近似，列表页的量只能靠前端。** 详情页要渲染就必然调用 `/post/single/get`，后端数接口调用量就够了；但列表页一屏 20 条只有一个接口，**后端根本不知道哪几条被真的看到了**。这就是「必须做前端曝光埋点」的核心论证。

> **源码里的两个旁证**（面试时说出来很有说服力）：
> - 项目里已经有一个「浏览记录」页（[pastPost.js](../../../../../tripleuni-frontend-wechat/pages/pastPost/pastPost.js#L60-L64) 的 `type: view` → `/post/list/view`），说明**后端已经在记录「谁看过哪些帖子」**；可前端从没主动上报过，所以这份记录的触发点只可能是详情接口被调用本身——**接口调用量 ≠ 内容被看到**。
> - `/post/single/report` 是「**举报**」不是「上报」（[detail.js](../../../../../tripleuni-frontend-wechat/pages/detail/detail.js#L155)），命名撞车，别在面试里讲混。

**第二步：曝光的双阈值判定。**

- 用 `wx.createIntersectionObserver()`，把阈值配成 `[0, 0.5, 1]`，只在 `intersectionRatio >= 0.5`（露出过半）时开始计时；
- **再加时长阈值**：连续可见 **≥ 1000ms** 才计一次——没有这一条，快速滑过的卡片会被误计成曝光；
- **本次停留内去重**：同一个 `post_id` 在本次页面停留内只上报一次（内存里记已报过的 ID）；
- **未达阈值就丢弃**：`onHide` / `onUnload` 时，把还在计时的记录直接丢掉，不补报。

**第三步：坑在「和长列表虚拟化打架」。**

节点被回收复用之后，观察器对象的引用和卡片上显示的业务 ID 会错位——A 卡的观察器复用到 B 卡的位置上，就会**把 B 的曝光记到 A 头上**。这种错位不会报错，只会让数据静默失真。所以：

- 业务 ID 必须从节点的 `data-id` 取（观察器回调里也会带 `dataset`），**不能依赖节点引用或 `index`**；
- 节点复用时需要重新 `observe`。

反过来，虚拟化对埋点其实是**利好**：只有可视区有节点，观察器数量天然被限制住，不用为几百条数据各挂一个观察器。

**第四步：上报与展示必须解耦。**

```text
前端埋点 ──上报事件──> 上报接口 ──> 日志 / 队列 ──> 分钟级聚合 ──> 帖子表 / Redis
                                                                     └─> 列表接口带回 ──> 前端渲染
```

- 前端上报的是**事件**（谁、看了哪条、看了多久），**不是数值**；「浏览量」是后端聚合出来的；
- 前端**绝不做本地 `+1`**：会重复计数、会和后端对不上、刷新时跳变；
- 代价是**自己刚看过的内容不会立刻计数**（聚合是分钟级的）。要么接受这个延迟，要么详情页接口直接返回实时值——但要清楚这是两个数据源，别混着报数。

**第五步：上报本身要「不参与业务」。**

- 客户端**攒批**（满 10 条 / 每 5 秒 / `onAppHide` 兜底），一次请求发一个数组，避免每条曝光一个请求；
- 每条记录带 `event_id`（uuid），后端按它**幂等去重**，防重复上报；
- 失败**不重试**、**不弹 loading**、超时不阻塞渲染——浏览量的数据丢一点可以接受，卡住用户不行；
- 上报走**独立域名**（就是那个被注释掉的 `report2023.tripleuni.com` 的思路），不占业务域名，也不占 `wx.request` 的 10 个并发额度；
- 必带字段：`event_type` / `post_id` / `user_serial` / `session_id` / `page` / `position` / `duration` / `client_ts` / `app_version` / `net_type`。缺 `app_version` 就没法做发版对比，缺 `session_id` 就串不起一次会话。

**第六步：最容易被忽略的一环——埋点自身的监控。**

| 要监控什么 | 为什么 |
|---|---|
| 上报成功率、队列丢弃量、平均批量大小 | 埋点服务挂了前端**不会报错**，只会数据静默消失 |
| 客户端异常：`wx.onError` / `wx.onUnhandledRejection` | 有异常但没埋点，等于线上故障靠用户投诉来发现 |
| 接口健康度：失败率、错误码分布（801/802 登录失效、901 维护）、`profile` 的 TTFB | 把「网络慢」和「服务端慢」分开 |
| 业务指标：到达率、曝光量、有效曝光率 | 数据合理性校验——某天曝光量翻 10 倍，先怀疑埋点重复上报，别先庆祝 |

**量级与防刷**（社区产品必然遇到）：

- 曝光是**最容易爆量**的埋点：一屏 3 条 × 每次启动 × 全部用户 = 每天百万级事件。所以要在客户端就去重、按用户 hash 采样，并让独立服务承载，不能打爆业务接口；
- **PV 天然可被脚本刷**，校园社区里"刷热度"是真实动机。所以对外展示优先用 **UV** 口径，按「用户 × 帖子 × 天」去重，并对异常流速设告警——单用户 1 分钟曝光 500 次就该报警，而不是等它刷上去。

#### 口述话术

> 「埋点这块我的判断是：难的不是写上报接口，是口径和链路设计。比如要做『帖子浏览量』，第一步不是写代码，是定义口径——曝光 PV、曝光 UV、详情进入 PV 是完全不同的三个数。而且详情页的量后端数接口调用量就够了，列表页的量只能靠前端，因为一屏 20 条只有一个接口，后端不知道哪条被看到了。所以前端必须上 `IntersectionObserver` 做『可视区比例 + 停留时长』双阈值判定。这里还有个坑：我们列表是虚拟化的，节点会回收复用，观察器引用会错位，所以业务 ID 必须从 `dataset` 取。最后上报和展示必须解耦，前端上报的是事件不是数值，绝不能本地 `+1`。另外埋点自己也要被监控——它坏了前端不会报错，只会数据静默消失。」

## 三、你是怎么优化首屏加载时间的？怎么记录的？

### 3.1 已落地的优化

优化内容见第一部分 1.1 与 1.2，这里只列清单便于口述时快速对答：

| 手段 | 解决的问题 |
|---|---|
| 资源上 CDN | 图片下载链路长、首字节慢 |
| imageCache 本地文件缓存 | 冷启动重复下载大图 |
| 缓存命中跳过图片资源接口 | 首屏少一整轮 RTT |
| URL 版本比对 | 缓存与后端数据不同步 |
| 后端分页（约 20 条/页） | 首屏 payload 随数据量增长 |
| 阈值预加载 | 快滑时数据未就绪 |
| 请求锁 + 终止标记 | 快速滚动重复请求 |
| 长列表虚拟化 | 节点数随滚动线性增长 |
| 开屏四路并发 + 计数收口 | 开屏等待策略 |
| 按需注入 / 骨架屏 | 首屏白屏与无用组件注入 |

### 3.2 首屏的最大瓶颈（主动抛出，加分项）

首屏的四个数据请求实际上被登录校验串住了：页面要等 `/user/check/wechat` 返回、`token_checked` 置位之后才发起 `initializeWhenReady`。所以真正的关键路径是**「登录校验 → 数据请求 → 渲染」**，图片缓存只是减少了最后一步的等待。

**可以提的下一步**：让校验与数据请求并行，无 token 时走游客态兜底，直接把这段串行砍掉。

### 3.3 追问：小程序和 Web 端分别怎么取首屏时间？

**微信小程序端**

`setData` 的回调只代表数据层同步完成，不保证渲染层已经绘制。要测到「内容可见」需要：

1. 在 `setData` 回调里再套一层 `wx.nextTick`，把终点打在下一帧之后；
2. 或改用官方的 `wx.getPerformance()` / `PerformanceObserver`（基础库 2.11.0+）取渲染相关指标。

> ⚠️ 这一条建议讲之前回官方文档确认一遍 API 语义。

**Web 端**

用 Performance API，不要用 `Date.now()`：

- 起点：`performance.timeOrigin` / `PerformanceNavigationTiming`（`responseStart`、`domContentLoadedEventEnd`）
- 终点：`PerformanceObserver` 监听 `paint`（FCP）与 `largest-contentful-paint`（LCP）
- 上报：`navigator.sendBeacon()`，避免阻塞页面卸载

### 3.4 记录方式的缺口

**当前没有自建的首屏耗时埋点。** 我是靠真机体感 + 性能面板发现问题并验证效果的，不是靠线上数据。这一条列在第四部分待改进项，被问到就直说。

## 四、待改进项

### 4.1 ⬜ 首屏耗时埋点与上报

**现状**：项目里没有自建的耗时埋点。存在的 `content_loaded` 是一个 0→4 的**计数**，用来决定何时撤开屏，不是耗时；`onReady` 里的 2s / 5s 两个定时器是开屏兜底，也不是埋点。

**问题**：没有数据就无法量化优化收益，也无法定位是「登录校验慢」「接口慢」还是「渲染慢」。被问"优化了多少"时只能靠体感答。

**改进方案**：

1. 小程序端在 `onLoad` 记录 `t0`，在首批列表 `setData` 回调里再套 `wx.nextTick` 记录 `t1`，上报 `t1 - t0` 作为「首屏内容可见时间」；条件允许时改用 `wx.getPerformance()`；
2. 分段上报：banner / topic / ad / post 各自完成时间分开统计，才能定位长尾在哪个数据源；
3. 把已有的 `content_loaded` 计数事件同时打点，开屏时长与首屏数据完成时间可以交叉分析；
4. 上报异步、失败不重试、不阻塞渲染。

**口述话术**：「首屏埋点这块我目前只有计数、没有耗时，是个明确的缺口。如果补，我会先分四段埋……」

### 4.2 ⬜ 其他可提的改进点

- 首屏数据请求被登录校验串行阻塞，可以评估「校验与数据请求并行 + 无 token 走游客态兜底」；
- 列表里存在用 `index` 当 key 的分支，应统一换成业务 ID，避免复用错位；
- **埋点与监控整体缺失**（方案见 2.5）：前端零上报、无异常捕获，线上问题只能靠用户反馈发现；「浏览记录」这类已有数据的触发点不可控，对外说不清口径。补的顺序建议是——先异常监控与上报通道，再曝光类埋点。
