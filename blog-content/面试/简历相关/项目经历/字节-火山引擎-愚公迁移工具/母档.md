# 母档：ByteHouse 愚公迁移工具前端

愚公是 ByteHouse（火山引擎云数仓）自研的一站式数据迁移工具，让用户把 ClickHouse、Doris、StarRocks、MaxCompute、Hive 等多种数据源的表结构与数据搬进 ByteHouse 企业版。前端要覆盖的主链路是：建迁移项目 → 选源/目标并做连通性测试 → 选库表 → 套转换规则 → 生成并确认 DDL → 建库表 → 同步分区 → 确认导入导出 SQL 与调度策略。我在职期间独立负责这个工具的前端开发，同时参与 ByteHouse 官网的日常维护。

最值得讲的有三件事：把创建迁移任务的十来种模式收敛成一套配置驱动的工作流；把两代后端接口规范（RPC 的 `Action=` 与 RESTful 的 `/openapi/v2/*`）收口到一个 HTTP 类封装的多个实例里，让业务层不用写解包判断；以及用「按引擎类型取渲染函数」的方式做动态表单，覆盖源/目标引擎组合带来的字段爆炸。

需要先说清边界：下面的代码结构、字段与分支都以本机源码快照为准（`apps/migrator/src`，读取日期 2026-09-10，无 Git 元数据）。而「我独立负责这条线」「重构减少过千行重复代码」「首屏优化近 30%」这类归属与数字，来自我本人提供的简历自述，快照本身无法证明，本文会逐条标出，不把它们混成已核验事实。技术实现细节与异常分支见 [技术实现概要.md](./技术实现概要.md)。

## 1. 背景与目标

迁移工具的复杂度不在单个页面，而在「维度相乘」：源端有 ce、cdw、clickhouse、doris、starrocks、hologres 等多种类型，目标端有 ce/cdw，迁移方案又有新建、断点续传、新增表、增加分区、TOS 文件导入、同集群 insert 等区分。每个组合的字段、校验、接口调用顺序都不一样，而流程骨架（选库表 → 转换 → 建表 → 分区 → 确认 SQL）是共享的。

这次交付要解决的就是这个矛盾。项目的目标是：让开发新增一种迁移模式时，不必再复制一整套页面；让用户在第 4 步刷新浏览器后能回到第 4 步、并且之前选过的库表还在；让两代后端接口的差异不外泄到业务代码里。成功的样子是——新增模式只改配置与少量 payload 转换，引擎字段差异只改连接的渲染分支，而流程引擎、页面骨架、Header/Footer 不动。

## 2. 个人职责和边界

我负责的是前端这一侧：跟后端约定接口、设计前端的流程与数据流、实现页面与组件、联调和修 Bug。具体来说，本人自述与快照可以相互印证的产出集中在四块——创建任务流程的重构（`pages/project/create-task`）、规则管理与 SQL 转换模块（`pages/rules`、`pages/tools/transformer`）、HTTP 请求封装（`services/request`、`services/common-http.ts`）、以及列表与通用表格能力（`common/components/common-table`、各列表页）。简历另提到「参与维护数据平台 smart-table 智能表格包」，该包不在本次快照内，无法核验，本文不展开。

我没做和不属于我的部分也要讲清：迁移的调度、转换、导入导出都在后端，前端只负责把用户选择拼成请求、把结果可视化；两套后台的路由分流、布局与基础组件库（`@dp/react-component`、`@dp/formily-dprc`、`@edenx/runtime`）是团队既有基建，我是在其之上做业务；EMR 侧那套「大数据迁移工具」（旧版迁移任务、数据连接、数据校验）与愚公共用同一份构建，我读到的部分是共用组件与数据层，不宣称整条 EMR 线由我实现。

## 3. 最难的问题

### 3.1 十来种迁移模式如何共用一套流程

最直接的困难是模式数量：快照里 `taskFlows` 一共定义了 10 个流程键，从 `create`、`continue`、`add_tables`、`partition`，到 TOS 导入的三兄弟 `tos_import / tos_import_continue / tos_import_add_tables`，再到同集群的 `insert` 系列。它们共享 8 个原子步骤中的大部分，但步骤序列不同：`tos_import` 用第 8 步「导入分区」替换了「转换规则 / 生成 DDL / 创建库表」，`partition` 只有一步，`continue` 少了第一步。

按旧写法，每种模式一套入口文件，改一个 Header 就要同步改三四份。我把它拆成两层：`stepComponentRegistry` 只负责「第 N 步长什么样」，`taskFlows` 只负责「这个模式按什么顺序走这些步骤、每步提交什么 action」。真正驱动流转的 `useTaskFlow` 因此可以写得很薄——「下一步」只做一件事：从配置里取出当前步骤的 action 名，在 `actions` 调度表里找到对应函数执行，成功后再移动指针；`action` 为 `null` 的步骤就纯展示、只翻页。页面骨架也不再关心模式：Header 只吃 `stepsToDisplay`（步骤号查注册表得到的标题列表），Footer 只吃首末步与 loading 标志。

难点不在数据结构本身，而在「做得太薄会漏掉模式特有的副作用」。举两个例子：`confirmTable` 在不同模式下要串联不同的接口——普通模式是「更新目标库 → 补全元数据 → 确认库表」并配一个固定百分比的进度弹窗，TOS 模式则要先按 `db.Tables` 拍平出已选表再走 `convertTosTablesToConfirmRequest`；`confirmExchangeSql` 在周期同步（`active_sync_mode === 'periodic'`）时根本不是提交迁移，而是把符合条件的表逐条构造成数据同步任务再 `Promise.all` 批量创建（全表模式只校验勾选和调度策略，分区模式还要求已校验、有规则、有数据周期）。这些都被放进各自的 action 实现里，而不是散进组件。因此新增模式只有在引入新 action 时才需要动引擎。

第二个难点是断点续传的数据一致性。用户在流程中途刷新，后端只在任务上记录了 `current_stage`，表单里的库表树、DDL 结果、分区数据都不在前端。我的做法是 URL 携带 `migrate_id` 与 `mode`，`useTaskFlow` 在 continue 类模式下用 `current_stage` 经 `mapCurrentStageToStep` 反查出步骤下标作为初始指针，再由 `use-restore-task` 在「continue + 首步」条件下按当前步骤分别回填：第 3、6 步拉库表并按 `selection_status` 过滤成树，第 5 步顺带重建建表结果，第 7 步拉分区数据再拍平回填。这里必须克制：恢复只在流程首屏做一次，恢复失败只提示、不阻断用户继续操作，避免「恢复逻辑本身把用户卡住」。快照可证这套结构存在并覆盖第 3、5、6、7 步；第 1、2 步不参与恢复，因为那时 `migrate_id` 尚未产生或仅有连接配置。

### 3.2 两代后端接口规范并存，差异不能外泄到业务代码

愚公前端同时对接两类后端：老服务走 RPC 风格，URL 形如 `ListMigrationJob`、`UpdateMigrationJobStatus`，成功时业务数据在 `response.data.Result`，错误藏在 `ResponseMetadata.Error`；新服务走 RESTful，形如 `/openapi/v2/...`、`/openapi/v3/...`，成功时是 `response.data.data`，错误形态则更多——`{code: 401, message}`、`{error: {full_message}}`、`{code, message}` 都出现过。

如果每个 API 函数自己判断，就会出现几十处重复的解包与错误分支。我在底层写了一个 `RequestClient` 类，把四个拦截器（请求/请求错误/响应/响应错误）都设计成**可整体注入**的参数，`common-http.ts` 用同一个类派生三个实例：RPC 老接口、校验工具、愚公新接口，各自配不同的 `baseURL` 与响应解包策略。业务层拿到的直接是有效数据，不需要写 `if (res.code === 0)`。错误侧统一在拦截器里收敛成 `Error`，业务层只需 `Message.error(err.full_message || '默认文案')`。

具体到实现，`bytehouseHttpClient` 的响应拦截里留了一个刻意的逃生口：`config.isCustomProcess` 为真时返回完整 `response.data`。这是为批量 SQL 转换列表接口准备的——它需要保留顶层的 `Page` 分页元信息，而默认解包会把这一层剥掉。为它单独再建一个实例不值得，加一个开关更划算。同时 401 被统一处理：清掉本地 `token` 与 `userInfo` 后强制跳转登录页。

### 3.3 引擎组合爆炸下的连接表单

源端与目标端各有多种类型，同一个「连接配置」区域在源和目标两处出现，字段却按类型不同：ce 要账号名、账号 ID、地域、AK/SK、用户、集群；cdw 要 Token、账号 ID、地域、计算组、网关地址；clickhouse/doris 等则要集群名、用户名密码、节点列表、S3 协议等，甚至「空密码」这种有语义的勾选项。

我的做法是把「类型 → 渲染函数」做成注册表：`type-schema.tsx` 导出 `{ ce, cdw, default, tos_import }`，每个值是一个接收 `namePrefix` 的函数，内部用 Formily 的 `Field` / `ArrayField` 声明字段；调用处只写一次 `(formSchema[类型] || formSchema.default)({ namePrefix: 'source_config.' })`，同一套连接表单就在源、目标两处复用，靠前缀决定字段落到 `source_config` 还是 `target_config`。字段之间的联动交给 `reactions`：密码是否必填取决于引擎与「空密码」勾选，S3 协议、覆盖导出、空密码等字段只在特定源类型下可见，cdw 的地域选项还会根据「是不是目标端、目标是不是 cdw」在两张选项表之间切换。

这里踩过一个值得说的坑。集群和用户下拉在选中后要同时写入 `cluster_id/cluster_name`，最初用 `form.setValues` 写，结果值落到了表单根路径，导致连通性测试在 `target_config` 下取不到集群名、测试直接失败。修复方式是用 `form.setValuesIn(\`${namePrefix}cluster_name\`, ...)` 写到正确路径。源码里把这个原因直接写成了注释，说明当时是定位完才改的，不是一次写对。

## 4. 关键技术决策及备选方案

### 4.1 为什么用「配置驱动 + 引擎」而不是每模式一个入口

候选方案有三个：保持每模式独立入口（重构前形态）、在一个组件里用 `if-else/switch` 按模式分支、以及配置驱动。第二个方案其实能跑通，但会把「模式特有逻辑」和「流程控制」揉进同一个组件，模式越多分支越深，新增模式仍然要改核心文件，违反开闭原则。独立入口的问题更直接：Header、Footer、步骤跳转、API 调用重复率极高，改一处通用 UI 要同步改多份。

选配置驱动的理由是可验证的：新增模式的工作量收敛到「在 `taskFlows` 加一个键」，只有引入新原子步骤或新 action 时才动注册表与调度表（快照里 10 个流程键只有 8 个原子步骤，就说明大部分复用成立）。代价也真实存在：配置表与组件注册表是两处需要同步维护的清单，`steps` 里写错步骤号只有运行时才暴露；`taskFlows` 与 `actions` 在快照里都是 `any`，字符串 action 名没有类型约束，改错名字不会编译报错。所以它换来的是扩展性，不是类型安全。

### 4.2 为什么用多实例而不是单实例 + 业务层判定

除了上面的多实例方案，另外两条路是：只留一个客户端、在每个 API 函数里判断该解包 `Result` 还是 `data`；以及每个接口各建一个实例。前者会把网关差异扩散到所有业务文件，且错误处理无法统一；后者实例数量失控，配置重复。多实例的边界很清楚——差异只有三处（baseURL、成功解包、错误判定），正好对应三个实例。放弃「一个客户端的通用解包」的原因是：解包规则本身没有通用解，`Result` / `data` / `response.data`（自定义处理）三种语义必须由发起方或实例来选；把它做成可配置开关却只服务一个接口，就失去了通用性。

代价是新增后端规范时要新增实例，团队需要知道「这个接口该用哪个 Client」。快照里的对应规则是：愚公新接口用 `bytehouseHttpClient`，EMR 旧接口用默认导出的 RPC 客户端，校验工具用 `validatorToolHttpClient`。

### 4.3 动态表单用渲染函数注册表，而不是 JSON Schema

「动态 schema」这个词容易让人以为是 JSON Schema 驱动。在本项目里我做的是渲染函数注册表：键是引擎类型，值是返回 `Field` 的 React 函数。另一条路是写 JSON Schema、配合 `SchemaField` 渲染，好处是配置可以序列化、理论上能由后端下发，甚至做成可视化编排。

我最终没走 JSON Schema，一个重要原因是这里的字段不是「普通输入框」：集群选择、用户选择、计算组选择都是带远程请求与联动行为的自定义组件，节点列表是 `ArrayField` + 自定义表格，密码必填性还要跟另一个字段联动。用 JSON Schema 表达这些，需要写大量 `x-component` / `x-reactions` 之类的约定，反而比直接写 JSX 更难维护、更难被类型系统保护。代价是这张表失去了「可序列化、可下发」的能力，属于用灵活性换扩展性的一次取舍。需要说明的是：快照里没有留下选型对比记录，「JSON Schema 方案」是我现在回看时认为值得评估的备选，不写成当时正式评估过的方案。

## 5. 结果与证据

已经落地、且本次读码可以直接核验的部分：

- 创建任务收敛为单一入口 `pages/project/create-task`，`config/flow.ts` 用一个步骤组件注册表（8 个原子步骤）与 10 个流程定义键描述全部迁移模式，Header/Footer/页面骨架不感知模式差异。
- 断点续传按 `current_stage` 反查步骤下标，并对第 3、5、6、7 步做数据回填。

- 连接表单用引擎类型注册表复用源/目标两处，并用 `reactions` 处理字段可见性、必填性与选项联动。
- 规则管理、SQL 转换（单条/批量）、项目与任务列表、通用表格（列选择持久化 + 自动省略 + 页码转换）均已接线可用。

## 6. 失败、复盘和后续改进

我在这条线上没有留下线上事故记录，也没有可核验的线上故障时间线，因此这一章不讲「事故复盘」，只讲读码后确认的问题和认知变化。

需要区分「当时就有」和「这次读码才发现」。下面几条都是**本次读码才发现**的实现层缺口，其中哪些当时已知、是否有排期，我没有材料，不做推断：规则列表的启用/停用、编辑、克隆函数已经写好但没接到列上（编辑与克隆只弹 `Message.info('WIP')`），真正可用的操作只有删除；分区规则的 `type` 编辑值域是 `datetime/string`，列表映射表却是 `{date, all}`，两者对不上导致列表回退显示原值；批量 SQL 转换表格提供了体积筛选，但父级只把状态筛选下发到请求，体积筛选没有落到接口；`constants.ts` 里的 `STATUS_OPTIONS` 与 `transfer-sql` 的 `getTransformerSqlBatchMetadata` 定义后无人调用。这些属于「已识别·未落地」。

更值得说的一个是**当时就该权衡、但实际留在了主包里的问题**：`App.tsx` 静态 `import * as monaco from 'monaco-editor'` 并注册四个语言 worker，Monaco 与 worker 因此进入入口依赖图。当时前端已经用路由级分包把各业务页面切了出去，但编辑器这类「重型且非首屏必需」的依赖没有单独异步化。现在我回看，如果再做一次，会把 Monaco 及语言包做成真正的动态加载（`React.lazy` 或组件内 `import()`），而不是停在路由级分包——不过我要说清，这是现在的判断，不是当时已经识别的问题，也不能直接当成「首屏 30% 优化」的因果证据。

认知上的变化有两点。第一，配置驱动不是免费的：配置表本身就是新的维护面，`steps` 与 `actions` 之间是「字符串弱约束」，如果重来一次，我会至少给 action 名加一个联合类型或常量枚举，把笔误挡在编译期。第二，动态表单的「schema」在字段带远程行为时会迅速退化成「写 JSX」，选型时应该先数清有多少字段是纯输入、多少字段带交互，再决定用 JSON Schema 还是渲染注册表。

## 7. 可能被追问的问题

**实现层：现在要新增一种迁移模式，我需要改哪些文件？**
最小改动是在 `config/flow.ts` 的 `taskFlows` 加一个键，从 8 个原子步骤里挑顺序、给每步配已有的 action；如果新模式引用了尚未存在的原子步骤，才需要在 `stepComponentRegistry` 注册组件；如果某一步的提交语义和现有 action 不同，才在 `use-task-flow.ts` 的 `actions` 里加函数，并在 `utils.ts` 补 payload 转换。这也是这套重构的意义：常规情况下不碰引擎和页面骨架。

**决策层：为什么 `steps` 里存的是 action 字符串，而不是直接存函数引用？**
存字符串的收益是配置可读、可比较，理论上能序列化（快照里 `taskFlows` 与 `stepComponentRegistry` 都是普通数据对象），也为「未来配置由后端下发」留了口子。代价是弱类型：字符串写错不会编译报错，只能运行时发现。如果重做，我会用联合类型约束 action 名。这里要诚实：快照里配置表是 `any`，类型安全并没有真正落地。

**验证与边界层：断点续传怎么保证一致性？边界在哪？**
它不是靠前端缓存，而是靠「后端记 `current_stage` + 前端按步骤重新拉数据」。`mapCurrentStageToStep` 把后端阶段映射成流程里的步骤号，`use-restore-task` 只在 continue 类模式且处于流程首屏时触发，按步骤拉 `listDbTable` / `listMigrateMetadata` 再回填表单。边界有三处：只覆盖第 3、5、6、7 步，第 1、2 步不回填；`current_stage` 不在映射表内时兜底到第一步；恢复失败只提示不阻断。另外，数据一致性最终仍由后端保证，前端只是把服务端状态重新呈现出来。

**实现层：`bytehouseHttpClient` 里的 `isCustomProcess` 是做什么的？**
它是给批量 SQL 转换列表接口开的逃生口。默认解包会把顶层 `Page` 分页元信息剥掉，而那个接口要同时拿到列表和分页信息，所以允许调用方通过 config 声明「这次返回完整 `response.data`」。之所以不新建实例，是因为差异只有一个开关，独立实例的维护成本更高。

**验证与边界层：401 为什么用 `window.location.href` 跳转？代价是什么？**
因为要在登录态失效时立刻中断所有后续处理并回到登录页，用硬跳转最稳。代价是它是整页刷新，会丢掉当前 SPA 状态（比如创建任务填了一半的表单），而且多个并发请求同时 401 时会触发多次跳转。更细的做法是走路由跳转 + 清理在途请求，但当时没做。

**实现层：你说的「用 Formily 优化渲染性能」具体指什么？**
可核验的部分是：跨步骤数据共享用 `FormProvider` 的单一 form 实例，当前步骤被包在 `VoidField name={\`step_${currentStepIndex}\`}` 里，切步骤会卸载上一步的字段，避免所有步骤的字段同时挂在树上；字段级联动用 `reactions` 做，只在依赖值变化时改组件属性，而不是整页重渲染。边界也要讲清：这是「按步骤卸载 + 字段级反应」，不是精确的依赖收集，也没有留下前后性能对比数据。
