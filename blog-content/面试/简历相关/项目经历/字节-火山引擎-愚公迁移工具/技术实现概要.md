# ByteHouse 愚公迁移工具前端 技术实现概要

本文还原 ByteHouse「愚公」一站式数据迁移工具前端在某个源码快照下的实现。该前端是一个 React 单页应用：用户在「迁移项目」下创建迁移任务，逐步骤完成源/目标连接、库表选择、规则转换、生成 DDL、建库表、分区同步与导入导出 SQL 确认；同一份构建还按路径名分流出另一套「大数据迁移工具」（EMR）后台界面，两套界面共享 HTTP 数据层、通用表格与部分业务组件。

版本与读取范围：本文依据本地源码快照 `d:\projects\playground\blog\.tmp\src`（读取日期 2026-09-10）。快照无 Git 元数据，无法给出分支或提交号。按其中出现的 `apps/migrator/src/...` 路径推断，该快照对应 `apps/migrator/src` 目录，本文沿用相对路径书写（如 `services/common-http.ts`）。快照未包含各业务 `services/*/types.ts` 类型声明文件，也未包含任何测试文件，因此接口字段只能从调用处的实际取值确认，不能据类型定义断言完整契约。本文只覆盖下文文件树列出的模块；`pages/data-connection`、`pages/create-job`、`pages/data-validation-job` 等模块只读到与主链路相接的部分，未逐文件展开。配套的经历叙述见 [母档.md](./母档.md)。

## 全局运行链路

入口是 `App.tsx`：先配置 Monaco 的 worker 与 loader，再挂 `QueryClientProvider`（默认关闭窗口聚焦重取），随后由 `BrowserRouter` 渲染 `RouterViews`。`routers/index.tsx` 用 `window.location.pathname` 的前缀白名单区分两套后台：命中 `/bytehouse` 或 `bytehousePaths` 进入 `BytehouseRouter`，否则进入 `EmrRouter`；`App.tsx` 的 `getBasename` 用同一份白名单计算 basename，两处判断必须保持一致，否则刷新子路由会落到错误的应用。

创建任务的主链路是：项目详情页 → `/project/detail/:projectId/task/create?mode=...` → `create-task/index.tsx` 读 URL 上的 `mode` 与 `migrate_id` → `determineEffectiveMode` 结合项目 `migrate_mode` 修正模式（TOS 项目会把 `create/continue/add_tables` 映射到 `tos_import*`）→ `useTaskFlow` 按模式取出流程定义 → 逐步骤渲染组件并在「下一步」时执行该步骤绑定的 action → 全部完成后跳回项目详情。

一条关键失败链路在数据层：任意请求命中 `code === 401` 时，响应拦截器清除 `localStorage` 的 `token` 与 `userInfo`，用 `window.location.href = '/login'` 强制跳转并 reject，业务层不会再拿到该错误去做局部提示。

## 核心模块复刻

### HTTP 数据层：一个类 + 多实例 + 可注入拦截器

代码锚点：`services/request/request.ts` 的 `RequestClient`；`services/request/tools/interceptors.ts`；`services/request/tools/config.ts`；`services/common-http.ts`。

`RequestClient` 是唯一底层封装。构造函数把 `defaultInitConfig` 与传入 config 做浅合并（`headers` 单独合并），用 `axios.create` 建实例，再用 `extra?.xxx || 默认拦截器` 的方式注入四个拦截器——外部可以整体替换，而不是叠加。`get/post/patch/put/delete/del` 都用 `client.get<T, T>` 这类双泛型签名，让 TS 认为返回值就是 `T`；这一点之后由拦截器解包来兜住。

`defaultInitConfig` 写死了 `Content-Type: application/json`、`withCredentials: true`、`timeout: TIMEOUT`（600000ms）。

默认拦截器的行为是：

- 请求侧注入 `Authorization: Bearer ${localStorage.token}`；无 token 不写该头。
- 响应侧依次判断 `data.code === 401`（清登录态并跳转）、`data.error`（取 `full_message || message || '请求失败'` reject）、否则返回 `response.data?.data`。
- 错误侧处理 HTTP 401、axios 错误中的 `data.error`、以及 `data.code && data.message` 三种形态，其余原样 reject。

`common-http.ts` 用同一个类派生出三个实例，这是整个数据层最关键的设计：

| 实例 | 用途 | 成功解包 | 错误约定 |
|---|---|---|---|
| 默认导出 `axiosApi` | 旧 RPC 风格接口（`Action=...`、`commonHttp.post('ListMigrationJob')`） | `response.data.Result` | 先看 `ResponseMetadata.Error` |
| `validatorToolHttpClient` | 数据校验工具 | `response.data?.data`，blob 原样返回 | 默认错误拦截器 |
| `bytehouseHttpClient` | 愚公新业务（`/openapi/v2/*`、`/openapi/v3/*`） | 401 处理 → blob 原样 → `config.isCustomProcess` 返回整个 `response.data` → 否则 `response.data?.data` | `responseErrorInterceptor` |

`bytehouseHttpClient` 的 `isCustomProcess` 是一个刻意留的逃生口：批量 SQL 转换列表接口需要保留顶层 `Page` 分页元信息，就在调用处带上 `isCustomProcess: true`，避免为它单独再建实例。

### 创建迁移任务：配置驱动的有限状态工作流

代码锚点：`pages/project/create-task/config/flow.ts`、`hooks/use-task-flow.ts`、`hooks/use-restore-task.ts`、`index.tsx`、`utils.ts`。

流程被拆成两层数据结构。第一层是原子步骤与组件的映射，共 8 个：

```ts
export const stepComponentRegistry: any = {
  1: { title: '迁移源&目标源', component: CreateTaskFirstStep },
  2: { title: '迁移对象', component: CreateTaskSecondStep },
  3: { title: '转换规则', component: CreateTaskThirdStep },
  4: { title: '生成DDL', component: CreateTask4Step },
  5: { title: '创建库表', component: CreateTask4_2Step },
  6: { title: '数据迁移', component: CreateTask5Step },
  7: { title: '迁移配置', component: CreateTask6Step },
  8: { title: '导入分区', component: CreateTaskImportPartitionStep },
};
```

第二层是「模式 → 步骤序列」的流程定义，快照中共 10 个 key：`create`、`continue`、`add_tables`、`partition`、`tos_import`、`tos_import_continue`、`tos_import_add_tables`、`insert`、`insert_continue`、`insert_add_tables`。每个步骤是 `{ step, action }`，`action` 为 `null` 表示该步只展示、不需要提交：

```ts
create: {
  title: '创建任务',
  steps: [
    { step: 1, action: 'createMigrateInfo' },
    { step: 2, action: 'confirmTable' },
    { step: 3, action: 'transformTableWithRule' },
    { step: 4, action: 'confirmDdlAndCreateDbTable' },
    { step: 5, action: null },
    { step: 6, action: 'syncPartitionInfo' },
    { step: 7, action: 'confirmExchangeSql' },
  ],
},
tos_import: {
  title: '创建任务',
  steps: [
    { step: 1, action: 'createMigrateInfo' },
    { step: 2, action: 'confirmTable' },
    { step: 8, action: 'importTosFile' },
    { step: 6, action: 'syncRuleInfo' },
    { step: 7, action: 'confirmExchangeSql' },
  ],
},
```

`useTaskFlow(mode, form)` 是引擎。它先按模式取 `flowConfig`，再决定初始指针：`continue` 类模式用 URL 上的 `current_stage` 经 `mapCurrentStageToStep` 反查步骤下标，其余从 0 开始；找不到下标时兜底为 0。随后维护 `currentStepIndex`，由它推出 `curStep` 与当前渲染组件。

推进逻辑刻意做得很薄——把「下一步」交给配置里的 action 名：

```ts
const handleNextStep = async () => {
  const actionName = flowConfig.steps[currentStepIndex]?.action;
  if (actionName && actions[actionName]) {
    await actions[actionName]();
  } else {
    stepUp();
  }
};
```

`actions` 是把字符串映射到异步函数的调度表，每个函数负责拼 payload、调用对应 service、成功后 `stepUp()`。其中三个 action 不只是转发：

- `createMigrateInfo`：先 `form.validate()`，对 `insert` 模式把源端集群信息复制到 `target_config`，`tos_import` 模式清空 `source_config`；捕获到 `Duplicate entry ... migrate_info.uniq_account_migrate` 时，把任务名改成 `${原名}_${HHmmss}` 后自动重试一次。
- `confirmTable`：按 `db_target_map` 逐个调 `updateDatabaseTarget`，再用固定百分比（20 / 45 / 85）驱动一个「正在补全库表信息」的进度弹窗，过程中先 `completeTableMetadata` 再 `confirmTable`；`tos_import*` 走另一条 `flatSelectedTables` 分支；`finally` 里关闭弹窗。
- `confirmExchangeSql`：当 `active_sync_mode === 'periodic'` 时不是提交单次迁移，而是把 `periodicSyncData` 过滤（全表模式只校验勾选与调度策略；分区模式还要求 `is_validated && rule_id && data_cycle`）后逐条构造 `CreateDataSyncTaskRequest`，用 `Promise.all` 批量创建周期同步任务。

加载态用 `loadingMap`（步骤号 → 布尔）汇总，`isLoading` 由 `loadingMap[curStep]` 得出；`partition` 模式是个例外：进入该模式时用 `isAutoSyncTriggered` ref 保证只触发一次 `syncPartitionIncrement`，并且 `transformerExchangeSql` 成功后不 `stepUp`（单步流程）。

断点续传由 `use-restore-task.ts` 负责。仅在「continue 类模式 + 当前处于流程首步 + 有 `migrate_id`」时启用，按 `curStep` 分别恢复：第 3、6 步用 `listDbTable` 过滤出 `selection_status` 为 `SELECTED`/`PARTIAL_SELECTED` 的库表，映射成树写回 `form.tables`；第 5 步在 `listDbTable` 回调里直接调 `createDbTable` 以恢复建表结果；第 7 步用 `listMigrateMetadata` 拉分区数据并 `flattenTable` 后写回 `dbDataWithPartitions`。恢复失败只弹 `Message.error` 并 `console.error`，不阻断页面。

页面装配见 `index.tsx`：`FormProvider` 包住 `FormLayout`，当前步骤组件被包在 `VoidField name={\`step_${currentStepIndex}\`}` 里，因此切换步骤会卸载上一屏幕的字段；`CreateHeader` 只吃 `stepsToDisplay`（由步骤号查注册表得到的 `{title}` 列表）画 Steps，`CreateFooter` 只吃 `isFirstStep/isLastStep/isLoading` 决定按钮。也就是说，增加一种模式不需要动 Header、Footer 与页面骨架。

真实输入走查：`mode=create` 且非 TOS 项目时，`determineEffectiveMode` 返回 `create`，流程 7 步；`mode=continue&current_stage=CONFIRM_DB_TABLE` 时映射到步骤 3，`initialStepIndex=1`，首屏直接落在「转换规则」并回填已选库表。异常路径：`current_stage` 不在映射表内时 `findIndex` 返回 -1，被 `initialStepIndex === -1 ? 0 : initialStepIndex` 兜成第 0 步。

### 引擎差异表单：以渲染函数注册表实现的动态表单

代码锚点：`steps/type-schema.tsx`、`steps/oss-schema.tsx`、`steps/CreateTaskFirstStep.tsx`。

源/目标端有 `ce`、`cdw`、`clickhouse`、`doris`、`starrocks`、`hologres` 等多种类型，字段差异很大。这里的「动态 schema」不是 JSON Schema，而是一个**键为类型、值为渲染函数的对象**：`type-schema.tsx` 的默认导出形如 `{ ce: ({namePrefix, isClone}) => <>…</>, cdw: …, default: …, tos_import: () => <></> }`，`oss-schema.tsx` 同理（按 `tos_import` 与中转模式分键）。

调用处只做一次按类型取函数并执行：

```tsx
{form.getValuesIn('source_config.source_type') &&
  (formSchema[form.getValuesIn('source_config.source_type')] ||
    formSchema['default'])({ namePrefix: 'source_config.', isClone })}
```

每个分支内部用 Formily 的 `Field` / `ArrayField` 声明字段，`namePrefix` 决定它落在 `source_config.` 还是 `target_config.`，因此同一套「ce 连接表单」可以在源和目标两处复用。字段级联用 `reactions`：`cdw` 的地域选项会根据「是不是目标端 + 目标类型是否 cdw」在 `CDW_REGION_OPTIONS` 与 `CE_CDW_REGION_OPTIONS` 间切换；`default` 分支的密码 `required` 取决于引擎与「空密码」勾选，非 clickhouse 且未勾空密码才必填；`s3_mode`、`s3_truncate_on_insert`、`empty_password` 均只在 `source_type === 'clickhouse'`（或 `doris`）时 `visible`。

这里有一处被注释写明来龙去脉的修复：集群/用户下拉在 `onChange` 里必须用 `form.setValuesIn(\`${namePrefix}cluster_name\`, ...)` 而不是 `form.setValues`，否则值会落到表单根路径，后续连通性测试在 `target_config` 下取不到该值。源码锚点见 `type-schema.tsx` 中 `VolcClusterSelect`、`VolcUserSelect` 两处 `reactions` 的注释。

连通性测试的载荷也随类型分叉：`CreateTaskFirstStep` 的 `handleSourcePing/handleTargetPing` 先 `form.validate('source_config.*')`，`ce/cdw` 走 `account_id/user_id/cluster_id + migrate_config` 分支，其他引擎走 `node_list` 分支并把 `ShardNum/ReplicaNum/ServerPort` 转成数字。

### 规则管理与 SQL 转换

代码锚点：`pages/rules/**`、`services/transfer-tools/transform-rule/index.tsx`、`pages/rules/partition-rule/**`、`services/transfer-tools/partition-sync-task/index.tsx`；`pages/tools/transformer/**`、`services/transfer-tools/transfer-sql/index.tsx`。

规则模块有两条并存的子业务。「转换规则」走 `GET/POST /openapi/v2/transform/rule`、`DELETE /openapi/v2/transform/rule/{rule_id}`，响应取 `res.rule_list`，条目字段有 `ID / RuleName / SourceType / TargetType / RuleType / TransformType / MappingRule / CustomRule / ExtraRule / Description / UpdatedAt`，其中三个 Rule 字段是 JSON 字符串，列表用 `formatJsonRule` 压成 `k: v; k: v`。新建弹窗用组件库的 `Form.useForm()` 命令式校验（无 schema），动态性体现在按选项联动：仅当 `transform_type === 'dql'` 且 `rule_type ∈ {export, import}` 且源类型属于 `clickhouse/ce/cdw` 时才显示「列预处理」区块；`extra_rule` 需通过 `isValidJson` 校验，非法时直接禁用确定按钮，提交前会把 `column_preprocess` 重新塞回 `extra_rule` 再 `JSON.stringify`。「分区规则」复用同一套页面骨架，走 `/openapi/v2/partition/rule`，字段是 `name / type / partition_pattern`，时间字段是毫秒数。

SQL 转换页用 Tabs 分「单条」「批量」两种模式。单条同步调 `POST /openapi/v2/transformer_sql`，成功后取 `res.display.status === 'success'` 与 `res.display.sql`，用 `bravo-formatter` 格式化，格式化抛错则回退原始 SQL。批量是三步：`POST .../batch_transform/upload`（`FormData` 字段名 `file`，返回 `file_id/file_name`）→ `PUT .../batch_transform/{file_id}` 启动 → `GET .../batch_transform/list` 轮询列表（本快照未实现轮询，启动成功后仅手动 `refetch`）。批量列表接口是 `isCustomProcess` + 自定义 `paramsSerializer` 的典型用户：它要保留顶层 `Page.PageNumber/PageSize/TotalCount`，并把 `status` 数组序列化成重复键。

批量与单条的请求体差异集中在 `utils/payload.ts`：单条多传 `sql`，`database_name` 恒传（允许空串），批量仅在 `ddl` 时传；两者都只在目标为 `ce` 时附加 `cluster_name` 与数值化的 `account_id`；`product_name` 由目标引擎小写映射 `{ce, cdw}`，未命中兜底 `ce`。批量启动前有一串顺序校验：先文件、再源引擎、再目标引擎，`ddl` 必须填数据库名，目标为 `ce` 必须填集群与账号。

### 列表与通用表格

代码锚点：`common/components/common-table/**`、`utils/index.tsx`、`pages/project/list/**`、`pages/project/detail/**`、`pages/transfer-task/**`。

`CommonTable` 把三件事合在一起：列选择、自动省略、分页归一化。列选择由 `useColSelect(columns, localClounmsKey)` 实现，只对带 `colFolding` 的列生效；勾选结果写进 `emrLocalStorage`（key 前缀 `emr_`），项目列表、项目详情与旧版任务表共用同一个 `main-cluster-list` key。自动省略由 `useColEllipsis` 实现，**只给没有 `render` 的列**注入渲染，空值统一显示 `-`，字符串套 `EllipsisTooltip`（真实溢出才弹）。分页归一化做了一层页码转换：后端分页从 0 开始、表格从 1 开始，因此非受控分页用 `transformPageNumToTable(pageNum)`（`!pageNum → 1`，否则 `+1`），回调再用 `transformPageNumToParam`（`!pageNum → 0`，否则 `-1`）还原。

列表页分成两种范式，快照里同时存在：

| | 愚公项目/任务列表 | EMR 旧版迁移任务 |
|---|---|---|
| 取数 | `useListManager` 一次拉全量 | `useQuery` 带 `PageNo/PageSize` |
| 分页 | 前端 `slice((current-1)*pageSize, current*pageSize)` | 后端分页，`current` 从 0 起 |
| 筛选 | 前端 `filterFn` + 列头去重生成的 `filters` | 请求参数 `JobName/JobId` |
| 复位 | `handleFilterChange` 把 `current` 重置为 1 | `handleFilterChange` 把 `current` 重置为 0 |

`useListManager` 的返回值把 `total` 覆盖为 `filteredData.length`，所以分页器显示的总是过滤后的条数；这也是它只适合数据量可控的列表的原因。

任务状态语义集中在 `pages/project/statusMap.ts`，共 8 张映射表：`migrateStatusMap`（19 个状态，如 `RUNNING/EXPORTING/IMPORT_DONE/MIGRATED/NONEED`）、`stageTextMap` 与 `stageTagMap`（10 个阶段，如 `SYNC_DB_TABLE`、`CONFIRM_PARTITION`）、`transformStatusMap`（5 个）、`syncStatusMap`（8 个）、`schedulerStatusMap`（5 个）、`dataSyncTaskStatusMap`（5 个）、`dataSyncExecutionStatusMap`（6 个）。项目详情表的操作列依据 `current_stage === 'CONFIRM_PARTITION'`（建表完成）与 `migrate_status` 决定显示「新增表 / 继续创建 / 停用 / 启用」，这些按钮拼出的 `mode` 正是 `create-task` 的流程键。

### 路由与首屏

代码锚点：`routers/index.tsx`、`routers/bytehouse.tsx`、`routers/emr.tsx`、`App.tsx`。

两套后台的业务页面都通过 `commonLoadable`（内部是 `loadable` + `import()`）注册，fallback 为空片段 `<> </>`，并带 `webpackChunkName` 注释，因此 create-task、project-detail、sql-transformer、data-comparison 等页面各自成为独立 chunk；`routers/bytehouse.tsx` 的首页、登录页与用户列表则是静态 `import`，构成入口首屏。这是快照里能直接证实的分包手段，注释里的 chunk 名也显示分包是按业务模块规划的。

需要注意 `App.tsx` 里 `import * as monaco from 'monaco-editor'` 与 `loader.config({ monaco })` 是静态引入——Monaco 及四个 language worker 会进入入口图。快照内没有 `React.lazy`/`Suspense` 包裹 Monaco 的写法，因此「重型编辑器是否已被切成异步 chunk」在当前快照下存疑，见后文局限。
