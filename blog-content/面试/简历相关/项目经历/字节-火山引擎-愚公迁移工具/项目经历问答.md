### 1.2 先统一 bug 数量的口径

简历写的是「参与 bytehouse 官网日常维护，累计修复 **10+** bug，完成 5+ 需求」，但错题集里记的是「你修了 **20+** bug」。两个数字必须先统一，否则面试官对着简历一问就露。

### 1.3 印象最深刻的 bug：Anchor 锚点闪回

**一句话结论**：Anchor 组件点击最后一个锚点时，会先高亮目标、滚动结束后又回退到上一个锚点。根因是**程序化平滑滚动与基于视口的 active 计算发生了竞态**，最终用「点击时锁定 active，直到用户主动滚动才解除」解决。

- **现象**：页面有 Part1/Part2/Part3 三个锚点，点 Part3 会短暂显示 Part3，滚动结束后立刻跳回 Part2。
- **触发条件**：最后一个锚点对应的 DOM 区域高度很小，且位于页面底部。
- **根因**：滚动结束重新计算可见性时，最后一个区域不满足阈值，组件就选了上一个满足条件的锚点。用户意图被自动逻辑覆盖了。
- **方案**：点击时 `isAnchorLocked = true` 并立即 `setActive(target)`；IntersectionObserver 回调入口先判 `if (isAnchorLocked) return`；监听 `wheel`/`touchstart`/`keydown` 检测到用户主动交互就解除锁定；再加 1.5–2s 超时兜底，防止永久锁死。

完整版见 [项目经历.md](../../项目经历.md#L24-L104)。

### 1.4 两个补强点

1. 「为什么不直接在 IntersectionObserver 里调阈值」——因为最后一个区块的自然高度不可控，调阈值治标不治本，锁住「用户意图」才是治本。
2. 文档里 `passive` 的写法自相矛盾：代码写 `passive: true`，注释却说「已使用 `passive: false` 因为需要 `preventDefault`」。面试前统一掉。

## 二、换到搬站平台（愚公）：难点是完全另一类

B 端中台没什么「首屏」问题，真正的难点在**状态与时序**：一个交互动作背后往往要串好几个接口，而这些接口之间有依赖顺序。

### 2.1 难点一：库表选择的「懒加载 + 勾选 + CSV 导入」三方时序

一个迁移任务要选几十上百张表，树上有几百个库、每个库几十张表，不可能一次拉全。

1. **懒加载**：树初始只有库节点，点库才去拉该库的表。用「已加载」和「正在加载」两个 `Set` 分别记账——前者让重复点击走缓存只展开不请求，后者防止并发点击时同一个库被拉两遍。
2. **勾选与加载的竞态**（最容易被忽略）：用户可能在表还没加载出来时就勾了**整个库**。这时选中集合里只有库的 key，等表拉回来必须把子表补进去。做法是额外记一个「待补选的库」集合——勾库时登记，加载完成后检查这个库是否需要补选，把子表补齐、**再把库的父键删掉**（树用的是 `SHOW_CHILD` 策略，只认叶子节点，留着父键会导致「已选」树渲染出空节点）。
3. **CSV 批量导入的时序最难**：用户上传 CSV 批量指定库表清单，但清单依赖的表数据**还没加载**。所以顺序必须是：解析 CSV 里出现了哪些库 → 触发这些库的加载 → **等它们全部加载完成** → 才能把 CSV 里的字符串路径映射成树节点的 key。
   实现上是三个状态接力：`正在处理的 CSV 批次` + `这批要等哪些库` + `已处理完批次`（防止同一个文件被重复解析）。
4. **筛选不能丢勾选**：按引擎 / 库名 / 表名筛选后点「全选」，只能选中**当前筛选结果**，既不能把没筛出来的也选上，也不能把之前已选的清掉。

**追问防线**

| 会被问 | 怎么答 |
|---|---|
| 为什么不一次拉全量？ | 几百个库 × 每个几十张表，首次 payload 和服务端压力都不可接受；且用户通常只关心少数几个库 |
| 用户勾了库但表还在加载，这时点下一步怎么办？ | 「已选」树和「下一步」的可用状态都是从同一个选中集合**派生**出来的，不存在「界面显示已选、提交却是空」 |
| CSV 里能不能写通配符？ | 支持 `*` 匹配该层所有子节点，解析时会展开成具体的表 key |
| 加载失败怎么办？ | 加载中的标记在 `finally` 里清理，失败只提示不清空已有勾选——不让用户前面的操作白做 |

### 2.2 难点二：一套流程编排要跑 5 种业务模式

创建迁移任务不是一个固定表单，而是**配置驱动的多步流程**。同一个入口要支持普通创建、对象存储文件导入、分区同步、周期同步，以及**从任务列表点「继续」回到中断的那一步**。

1. **流程是配置出来的**：一份 `taskFlows[mode]` 描述这个模式有哪几步、每步渲染哪个组件、点「下一步」该调哪个接口，组件集中注册。新增一种模式基本只改配置，不动流程代码。
2. **「继续」要能恢复到中断处**：URL 上带当前阶段，映射成步骤索引后作为这一步的「起点」——所以续接进来的流程，上一步按钮不会一路退回第 1 步。
3. **一步的 loading 不是单一的**：某个步骤要连续调两三个接口（先把选中库表的结构信息补全，再提交确认），所以用一张按步骤索引聚合多个请求状态的映射表，按钮的转圈才是对的。
4. **幂等处理**：任务名在同一账号下不允许重名，撞了之后后端返回的是 `Duplicate entry ... for key 'migrate_info.uniq_account_migrate'` 这种对用户完全不可读的报错。做法是识别这个错误后给任务名自动加时间戳后缀重试一次，用户无感。

## 三、formily 专项：技术原理与追问预测

> 对应简历原文：「使用 formily 处理前端表单，实现动态 schema，优化渲染性能」
> 源码依据：`.tmp/src` 中 `create-job` / `project/create-task` / `data-connection` / `create-validation-task` 等模块

### 3.0 ⚠️ 先说一个必须修的表述

源码里**没有任何 `createSchemaField` / `SchemaField` / `x-reactions`**——项目用的是 **JSX 声明式 `Field` + `reactions`**：

```jsx
<Field
  title="OSS Region"
  name="migrate_config.oss_region"
  decorator={[FormItem]}
  component={[Select, { options: ... }]}
  reactions={field => { ... }}   // ← 不是 x-reactions
/>
```

这两条路的追问方向完全不同：

| 简历措辞 | 面试官会问什么 |
|---|---|
| 「动态 schema」 | schema JSON 长什么样？`x-reactions` 表达式怎么写？`SchemaField` 怎么注册组件？ |
| 「声明式 Field + reactions」 | 受控还是非受控？联动怎么防循环？ |

**建议改成**：「用 formily 的声明式 `Field` + `reactions` 实现字段联动，替代手写受控表单」。

这样说的都是真做过的，且不损失分量——真正的亮点在 3.2 的 Q4 / Q5。

### 3.1 技术原理

#### 一、四层架构（最后一层本项目没用）

| 层 | 包 | 职责 |
|---|---|---|
| 内核层 | `@formily/core` | Form / Field 响应式领域模型，管状态与校验，**与视图框架无关** |
| 响应式层 | `@formily/reactive` | 自研响应式系统，参考 MobX，**强依赖 Proxy** |
| 桥接层 | `@formily/react` | 「渲染胶水层」——把 React 组件作为观察者接到模型上，本身不管数据与校验 |
| 协议层（可选） | `@formily/json-schema` | `SchemaField`，JSON Schema 驱动 |

#### 二、精确更新怎么实现：依赖收集

```javascript
const obs = observable({ aa: { bb: 123 } })

autorun(() => console.log(obs.aa.bb))   // 读 → 把「这个 autorun」登记为 aa.bb 的依赖
obs.aa.bb = 321                          // 写 → 只通知读过 aa.bb 的观察者
```

- **读（Proxy 的 `get`）时记录**「谁在读我」
- **写（`set`）时只通知**读过这个字段的观察者

所以改一个字段，**只有依赖它的组件重渲染**。官方口径是「依赖追踪，精确更新，按需渲染」。

`observable` 提供几种形态来控制响应粒度：

| API | 含义 |
|---|---|
| `observable.deep`（默认） | 深层响应 |
| `observable.shallow` | 只响应第一层 |
| `observable.ref` | 只有整体引用变化才响应 |
| `observable.box` | 单值 + `get` / `set` |
| `observable.computed` | 计算属性 |

`observer` 是把 React 组件接入这套系统的桥梁：它会自动收集组件 **render 过程中**读到的 observable 状态作为依赖。（`observer` 与 `Observer` 的关系 ≈ `memo` 与 `useMemo`）

#### 三、为什么比手写受控表单快

| | 手写受控表单 | formily |
|---|---|---|
| 值存在哪 | 父组件 `useState` | Form 实例（observable 对象） |
| 改一个字段 | 父组件 `setState` → **整棵表单子树重渲染** | 只有读该字段的组件重渲染 |
| 订阅粒度 | 组件级 | **字段级** |

一句话：**它是「非受控 + 字段级订阅」，不是「受控 + 组件级 diff」。**

#### 四、Form / Field 模型与生命周期

`createForm()` 创建实例即 **Init** → 视图层挂载时通过 `useAttach()` 挂载模型即 **Mount** → **Unmount**。这些节点都有对应 hook（`onFormInit` / `onFormMount` / `onFormUnmount`），字段级有 `onFieldValueChange` / `onFieldReact` / `onFieldInit`。

#### 五、主动联动 vs 被动联动（性能差异的关键）

| 写法 | 机制 | 特点 |
|---|---|---|
| `onFieldValueChange('a', cb)` | **主动**监听 a 的变化 | 命令式，需自己判断「值真变了没」 |
| `onFieldReact('b', cb)` | **被动**：回调里读了什么就依赖什么 | 走依赖收集，**性能更好**，官方推荐 |
| `reactions={fn}` | 字段自己的被动联动 | 同上 |

#### 六、一个反直觉的设计：声明式属性只在初始化生效

formily 2.0 **砍掉了受控更新**。`Field` 上的属性只在初始化时生效，之后要动态改必须走命令式 API：

```javascript
field.componentProps = { ... }                                            // 改自己
form.query('migrate_config.oss_region').get(f => f.setComponentProps(x))  // 改别人
```

官方原因：同时支持受控与非受控会产生大量边界冲突，而且为了兼容受控还要额外做一层**脏检查**，反而拖累性能，所以直接砍掉。

> 这解释了 [oss-schema.tsx](../../../../../.tmp/src/pages/project/create-task/steps/oss-schema.tsx#L185-L188) 里为什么用 `field.componentProps = {...}` 改选项，而不是在 JSX 上重新传 props。

#### 七、官方的一条使用建议（可以主动讲，显得懂设计意图）

> 「尽量避免以视图层框架的方式来用 formily」——比如 `form.setValues` 配 `useEffect` 去同步表单状态。

因为 formily 是**非受控**的：视图只是模型的观察者，不该反过来用 React 副作用去驱动模型。用命令式方式操作 formily，通常意味着设计上还有更好的方案。

### 3.2 追问预测（按概率排序）

#### Q1：formily 相比手写表单 / antd Form，性能优势在哪？

- **考察**：原理层。这题答不出，后面全崩。
- **回答要点**：核心是**订阅粒度**。手写受控表单值存在父组件 `useState`，任一字段变化 → 父组件重渲染 → 整棵表单子树跟着重渲染；formily 是**非受控 + 响应式**，字段值存在 Form 实例里，靠 Proxy 做细粒度依赖追踪，只有依赖该字段的组件重渲染。
- **加分句**：formily 2.0 的官方口径就是「最小订阅」——脱离事件流，不需要靠 `onFieldValueChange` 手动控制重渲染。
- **下一层**：`observable` 有几种形态？分别什么场景用？（deep / shallow / ref / box / computed）

#### Q2：你具体做过哪些联动？

- **考察**：是背概念还是真用过。**这题必须能报出具体字段名。**
- **回答要点**（两个真实场景）：
  1. **对象存储类型 ↔ 地域**（[oss-schema.tsx](../../../../../.tmp/src/pages/project/create-task/steps/oss-schema.tsx#L77-L107)）：`s3_type` 在「火山 TOS / 阿里 OSS / 腾讯 COS / AWS S3」间切换时，要把 `oss_region` **重置为新 provider 的默认地域**，同时把地域下拉的**选项列表整体换掉**。
  2. **引擎类型 ↔ 参数模板**（[CreateConnectionItemModal.tsx](../../../../../.tmp/src/pages/create-validation-task/components/CreateConnectionItemModal.tsx#L196-L207)）：`engine_name` 变化时，把「自定义参数配置」编辑器的内容换成该引擎的模板 `engine_template`。
- **下一层**：代码怎么写？（见 Q3）

#### Q3：联动的代码具体怎么写？

- **回答要点**：两种写法项目里都用了——

```javascript
// 写法一：函数式 reactions（字段自己订阅别的字段）
reactions={field => {
  const s3Type = field.form.getValuesIn('migrate_config.s3_type')
  field.componentProps = { ...field.componentProps, options: buildOptions(s3Type) }
}}

// 写法二：数组式 reactions + 内置 effect（监听目标字段变化）
reactions={[curField => {
  onFieldValueChange('engine_name', field => {
    curField.setValue(field.value ? engineTemplate : '{}')
  })
}]}
```

- **下一层**：为什么写法一改属性用的是赋值而不是重新传 props？（见 Q4）

#### Q4：`Field` 上直接写 `options={...}` 为什么不生效？🔥

- **考察**：formily 2.0 最容易踩的坑。**能答出来说明是真踩过，不是看文档抄的。**
- **回答要点**：formily 2.0 里 **`Field` 的声明式属性只在初始化时生效**，之后不会跟着 React 重渲染走。要动态改属性必须走命令式 API——`field.componentProps = xxx`，或 `form.query('a.b').get(field => field.setComponentProps(xxx))`。
- **加分**：官方砍掉受控更新的原因——受控与非受控并存会产生大量边界冲突，而且为了兼容受控还得额外做一层**脏检查**，反而拖慢性能，所以 2.0 直接不支持。
- **下一层**：那联动会不会把用户已经填好的值冲掉？（见 Q5）

#### Q5：联动会不会把用户已填的值冲掉？🔥

- **回答要点**：会，而且**首次渲染时最容易踩**——回填场景下 `reactions` 一开始就会执行一次，如果无脑重置地域，用户带着上次填的数据进来就会被冲掉。

做法是加一道「值真的变了」的闸门：

```javascript
const prevS3Type = field.data?.prevS3Type
if (!prevS3Type) { field.data = { ...field.data, prevS3Type: currentValue }; return }  // 首次只记录，不动手
if (prevS3Type === currentValue) return                                                 // 没变就不处理
// 只有真的换了 provider，才重置地域
```

- **加分**：这道闸门同时解决了**循环触发**——A 改 B、B 又反过来影响 A 时，靠「值没变就直接 return」掐断。
- **下一层**：如果联动链路更长（A→B→C）呢？（答：尽量让依赖单向，或改用 `onFieldReact` 让依赖关系由「读了什么」自动推导，而不是手工维护触发顺序）

#### Q6：你说优化了渲染性能，有数据吗？

- **考察**：风险题（简历写了「优化渲染性能」）。**源码里没有 benchmark，别编数字。**
- **回答策略**：诚实分层——
  1. 「没有做过前后 benchmark，因为当时场景字段量在几十个量级，体感上没有明显卡顿」；
  2. 「但选 formily 而不是手写受控表单，本身就是从机制上避免了整表重渲染：非受控 + 字段级订阅，改一个字段不会触发整棵子树」；
  3. 「如果真要量化，我会在 `onFormValuesChange` 上打点，统计单次变更实际触发重渲染的字段数」。

#### Q7：formily 有什么不好用的地方？

- **考察**：技术判断力。只会夸的人反而减分。
- **回答要点**：
  - 非受控 + 声明式属性只初始化生效，**心智负担**比手写受控高——想动态改属性必须记住走命令式 API，写 JSX 的直觉在这里会失效；
  - 容易写出「属性写了不生效」这类**静默 bug**，不报错，只是没效果；
  - 简单表单用它是**过度设计**，字段少、联动少的话 antd Form 更直接。

#### Q8：formily 和 antd Form / react-hook-form 怎么选？

- **回答要点**：看**联动复杂度**和**字段规模**。formily 的优势在「字段多 + 联动多 + 需要动态结构」的 B 端中台场景——这种场景下受控表单的状态管理会迅速失控；反过来说，3～5 个字段的登录表单上 formily 是杀鸡用牛刀。

### 3.3 三条别说的话

| 别说 | 因为 |
|---|---|
| 「`x-reactions`」「schema JSON」 | 项目没走 `SchemaField`，一问细节就露 |
| 「formily 底层做 diff / 虚拟 DOM 优化」 | 错。是 Proxy + Observable 的**依赖追踪**，不是 diff |
| 「渲染性能提升了 XX%」 | 没有 benchmark 支撑，被追问统计口径就崩 |

---

**一句话总结**：这段经历的得分点不在「用了 formily」，而在 **Q4 + Q5**——知道「声明式属性只初始化生效、动态要命令式」和「联动要加值变化闸门防冲值 / 防循环」这两条，能证明你是踩过坑的人，不是照着文档抄的。
