### 简短开场
**一句话结论**：我遇到的最深刻的 bug 是 Anchor 组件在点击最后一个锚点时会先高亮目标然后在滚动结束后回退到上一个锚点。我最终用“点击时锁定 active，直到用户主动再次滚动才解除锁定”的策略解决了问题，兼顾了用户意图和视口驱动的自动切换逻辑。

---

### 问题描述
- **现象**：页面有 Part1、Part2、Part3 三个锚点。点击 Part3 时页面平滑滚动到 Part3 区域并短暂显示 Part3，但滚动结束后立即从 Part3 跳回 Part2。  
- **触发条件**：最后一个锚点对应的 DOM 区域高度很小且位于页面底部。  
- **相关点**：Anchor 的 active 由视口位置或 IntersectionObserver 的可见性判断决定。

---

### 根本原因分析
- **竞态条件**：点击触发的程序化平滑滚动与基于视口的 active 计算发生竞态。  
- **可见性阈值问题**：最后一个区域高度不足，滚动结束后重新计算可见性时不满足阈值，组件选择上一个满足条件的锚点作为 active。  
- **意图与自动逻辑冲突**：用户点击表达了明确意图（想停在 Part3），但自动的可见性检测在短时间内覆盖了这个意图。

---

### 修复策略概述
**核心思路**：在用户点击锚点并触发程序化滚动时，临时“锁定” active 为目标锚点，阻止 IntersectionObserver 或视口计算覆盖该状态；当检测到用户主动交互（如滚轮、触摸、键盘）或超时/滚动结束时解除锁定，恢复自动切换。  
**不改动** IntersectionObserver 的判断逻辑，只在高层加一层意图优先的保护。

---

### 详细实现步骤
#### 锁定与立即高亮
- **步骤**：点击锚点时设置 `isAnchorLocked = true`，立即 `setActive(target)`，并调用 `scrollIntoView({ behavior: 'smooth' })` 或自定义平滑滚动。  
- **目的**：优先保证用户点击意图被视觉和状态一致地反映。

#### 让视口计算在锁定期间忽略更新
- **实现**：在 IntersectionObserver 回调或 `getCurrentAnchor` 的入口处先检查 `if (isAnchorLocked) return;`，锁定期间不更新 active。

#### 检测用户主动交互以解除锁定
- **监听事件**：`wheel`, `touchstart`, `keydown`（方向键、PageUp/Down 等）。一旦检测到，立即 `isAnchorLocked = false` 并清除 fallback 定时器。  
- **理由**：用户主动滚动表示意图改变，应立即恢复自动逻辑。

#### 处理平滑滚动中断与超时回退
- **中断处理**：如果用户在平滑滚动中手动滚动，交互监听会解除锁定并允许正常计算。  
- **fallback 保护**：设置短超时（例如 1.5–2s）作为兜底，防止因某些浏览器或异常导致永久锁定。

#### 代码示例
```js
let isAnchorLocked = false;
let lockFallbackTimer = null;

function onAnchorClick(href, targetEl) {
  isAnchorLocked = true;
  setActive(href);
  targetEl.scrollIntoView({ behavior: 'smooth' });
  clearTimeout(lockFallbackTimer);
  lockFallbackTimer = setTimeout(() => { isAnchorLocked = false; }, 2000);
}

function userInteracted() {
  if (!isAnchorLocked) return;
  isAnchorLocked = false;
  clearTimeout(lockFallbackTimer);
}

['wheel','touchstart','keydown'].forEach(e =>
  window.addEventListener(e, userInteracted, { passive: true })
);

const io = new IntersectionObserver(entries => {
  if (isAnchorLocked) return;
  // 正常的可见性判断并 setActive(...)
});
```

### 权衡 验证 与面试要点
- **优点**：实现简单、兼容性好、能立即修复用户可见的闪回问题；尊重用户点击意图。  
- **缺点**：需防止永久锁定（用超时）；必须正确检测并优先响应用户交互以避免阻塞正常行为。  
- **验证方法**：在不同页面高度、不同浏览器、不同滚动速度下做回归测试；覆盖点击后立即中断滚动、无中断正常滚动、以及键盘翻页等场景。  
- **面试回答要点**：说明你如何定位到是“可见性计算与程序化滚动的竞态”，为什么选择临时锁定（短期可交付）而不是直接改 IntersectionObserver 逻辑（长期可优化），并展示你考虑到的边界条件与验证策略。

---

### 结尾一句话
**总结陈述**：我用“点击优先、交互解除、超时兜底”的锁定策略解决了最后一个锚点闪回问题，既保证了用户意图的即时反馈，也通过交互检测和超时机制避免了副作用，后续可用 IntersectionObserver 优化为更稳健的长期方案。
4. 动态懒加载重库的原理？
### 快答
**通过 lazy load（动态导入）把“重库”拆成按需加载的 chunk，可以显著减少首屏需要下载、解析和执行的 JavaScript 体积，从而缩短首屏渲染和交互准备时间（FCP/TTI/LCP 等指标）并降低主线程阻塞。**   [CSDN博客](https://blog.csdn.net/qq_36287830/article/details/149362893)  [知乎专栏](https://zhuanlan.zhihu.com/p/7387742615)

---

### 原理详解
- **减少初始传输体积（Critical Payload）**  
  把大型 npm 包放到动态导入的 chunk 中，构建工具会把它从主 bundle 中拆出。用户首次打开页面时只下载主 bundle（更小），重库在真正需要时才发起请求，降低首包字节数与首屏网络负担。   [CSDN博客](https://blog.csdn.net/qq_36287830/article/details/149362893)

- **降低解析与编译开销**  
  浏览器在收到 JS 后不仅要下载，还要**解析（parse）和编译/优化（compile/bytecode/JIT）**。体积大的脚本会占用主线程更长时间，阻塞渲染与事件处理。延后加载重库能把这部分 CPU 开销移到用户真正触发功能时，缩短首屏可交互时间。   

- **缩短关键渲染路径与减少阻塞资源**  
  首屏关键路径只包含渲染必要的资源（HTML/CSS/少量 JS）。把非关键逻辑延后加载，能减少阻塞渲染的资源数量与大小，从而改善 FCP/LCP。   [

- **利用浏览器缓存与并发请求**  
  动态 chunk 可独立缓存；后续页面或交互复用时无需重复下载。现代协议（HTTP/2/3）允许并发请求多个小文件，配合合理的缓存策略能在总体上比单一超大 bundle 更高效。

    *   **Next.js Image 组件**: 广泛使用 `<Image />` 组件，自动处理懒加载 (lazy loading)、格式转换 (webp) 和尺寸优化 (srcset)，同时也使用了tinypng

3.  **渲染性能优化 (Rendering Performance)**

    *   **next/font/local**: `app/layout.tsx` 使用 `next/font/local` 加载自定义字体，实现了字体文件的自托管和预加载，避免了 CLS (Cumulative Layout Shift) 和 FOIT (Flash of Invisible Text)。
    *   **Font Loading Strategy**: `Page1` 中有字体加载检测逻辑 (`document.fonts.ready`)，确保字体加载完成后再展示内容，提升视觉体验。

二、 可提升的优化点 (Potential Improvements)

1.  **预加载策略增强 (Preloading Strategy)**
    *   **现状**: `Page1` 之后的内容完全依赖用户滚动触发加载。
    *   **建议**: 在用户浏览 `PageN` 时，静默预加载 `PageN+1` 的关键资源（特别是大图）。可以在 `onShow` 回调中触发下一页图片的 `preloadImage`。

2.  **JS 执行优化**
    *   **现状**: `PageManagerProvider` 中的 `wheel/touch` 事件监听虽然有 cooldown，但仍运行在主线程。
    *   **建议**: 考虑使用 Passive Event Listeners (已使用 `passive: false` 因为需要 `preventDefault`，这是权衡)。对于纯展示动画，尽量移除 JS 定时器 (`setTimeout` 动画序列)，改用 CSS Animation Delay 或 Web Animations API，减少 JS 线程占用。

3.  **Bundle 细粒度拆分**
    *   **现状**: 页面级拆分已做。
    *   **建议**: 检查第三方库（如 `recharts` 在 Page6/11/14 中使用）是否被重复打包或过早加载。如果图表只在特定页面出现，确保它们只在该页面的 Chunk 中。

4.  **DOM 节点数控制**
    *   **现状**: `pages-wrapper` 保留了所有已渲染的页面 (`isActive` 逻辑目前是 `page <= showUpTo`)。这意味着用户滚到第 20 页时，前 19 页的 DOM 都在内存中。
    *   **建议**: 实现“虚拟滚动”或“DOM 回收”机制。只保留当前页、上一页和下一页的 DOM，其他页面卸载或 `display: none` (React 中由 Key 控制卸载)，减少内存占用和样式重计算开销。
