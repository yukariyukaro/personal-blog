# 性能优化相关提问的思路
##  1.优化指标：
- 首屏速度、白屏时间等
- 操作速度以及渲染速度
白屏时间：资源加载时间、首屏js执行等
渲染页面：首屏数据请求、DOM渲染
首屏速度能做的操作：
- 收益很大的：减少首屏资源体积、异步加载（体积较大又不是马上要用的功能。如图片压缩功能）、使用库的新版本（有的库的旧版本不支持tree-shaking，如xlsx）
## 2.各项指标
- FCP: 首屏内容渲染时间，指用户首次与页面交互时，页面首次渲染出可见内容的时间。（加载动画算有意义的内容，因此，FCP并不能反映真正的首页加载完毕。）
- LCP: 最大内容渲染时间，指用户首次与页面交互时，页面首次渲染出最大内容的时间。（最大内容是指页面中可见的最大内容，如图片、视频等）
- TTI: 可交互时间，指页面可以响应用户输入的时间。

## 2. 项目中的运用

### 2.1 懒加载原理详解
- **减少初始传输体积（Critical Payload）**  
  把大型 npm 包放到动态导入的 chunk 中，构建工具会把它从主 bundle 中拆出。用户首次打开页面时只下载主 bundle（更小），重库在真正需要时才发起请求，降低首包字节数与首屏网络负担。   [CSDN博客](https://blog.csdn.net/qq_36287830/article/details/149362893)

- **降低解析与编译开销**  
  浏览器在收到 JS 后不仅要下载，还要**解析（parse）和编译/优化（compile/bytecode/JIT）**。体积大的脚本会占用主线程更长时间，阻塞渲染与事件处理。延后加载重库能把这部分 CPU 开销移到用户真正触发功能时，缩短首屏可交互时间。   

- **缩短关键渲染路径与减少阻塞资源**  
  首屏关键路径只包含渲染必要的资源（HTML/CSS/少量 JS）。把非关键逻辑延后加载，能减少阻塞渲染的资源数量与大小，从而改善 FCP/LCP。   [

- **利用浏览器缓存与并发请求**  
  动态 chunk 可独立缓存；后续页面或交互复用时无需重复下载。现代协议（HTTP/2/3）允许并发请求多个小文件，配合合理的缓存策略能在总体上比单一超大 bundle 更高效。  

---
- **First Contentful Paint（FCP）**：首包更小 → 更快拿到并渲染首个内容 → FCP 提升。  
- **Time to Interactive（TTI）/可交互时间**：减少主线程 JS 执行时间 → 更早响应用户输入。

### 2.3  年度总结

1.  **代码分割与懒加载、预拉取 (Code Splitting & Lazy Loading)**
    *   **动态导入 (Dynamic Imports)**: `components/Pages.tsx` 中使用了 `next/dynamic` 导入 `Page2` 到 `Page23`。
    *   **效果**: 首屏只加载 `Page1` 的代码，减少了初始 Bundle 体积 (FCP/LCP 提升)。
    *   代码引用: [Pages.tsx:L7-L25]
2.  **图片优化 (Image Optimization)**
    *   **Next.js Image 组件**: 广泛使用 `<Image />` 组件，自动处理懒加载 (lazy loading)、格式转换 (webp) 和尺寸优化 (srcset)，同时也使用了tinypng
    *   **优先级控制**: 首页 (`Page1`) 的前几张图片设置了 `priority` 和 `loading="eager"`，确保首屏 LCP (Largest Contentful Paint) 快速渲染。后续图片默认懒加载。
    *   **动态裁切服务**: `utils/resources.ts` 中封装了 `getOptimizedAIImageUrl`，使用 `wsrv.nl` 进行即时 WebP 转换和尺寸压缩 (`w=1000&output=webp&q=80`)。-

3.  **渲染性能优化 (Rendering Performance)**
    *   **CSS 动画优先**: 动画大量使用 CSS `transform` 和 `opacity` (在 `globals.css` 和各 module.css 中)，利用 GPU 加速，减少重排重绘。
    *   **will-change 提示**: 关键动画元素使用了 `will-change: opacity, transform`，提示浏览器提前优化图层。
    *   **requestAnimationFrame**: 虽然主要依赖 CSS，但在 JS 驱动的逻辑中（如 `page22.tsx` 的 `slideIn`），使用了 `requestAnimationFrame` 确保视觉更新同步。
    *   **IntersectionObserver**: `PageManagerProvider` 使用 `IntersectionObserver` 管理页面激活状态，避免了高频 scroll 事件监听带来的性能损耗（虽然内部也保留了 wheel/touch 监听用于翻页逻辑，但通过 `requestAnimationFrame` 或防抖/节流控制是常规做法，这里用了 cooldown 时间戳控制）。
4.  **字体优化 (Font Optimization)**
    *   **next/font/local**: `app/layout.tsx` 使用 `next/font/local` 加载自定义字体，实现了字体文件的自托管和预加载，避免了 CLS (Cumulative Layout Shift) 和 FOIT (Flash of Invisible Text)。
    *   **Font Loading Strategy**: `Page1` 中有字体加载检测逻辑 (`document.fonts.ready`)，确保字体加载完成后再展示内容，提升视觉体验。

二、 可提升的优化点 (Potential Improvements)

1.  **预加载策略增强 (Preloading Strategy)**
    *   **现状**: `Page1` 之后的内容完全依赖用户滚动触发加载。
    *   **建议**: 在用户浏览 `PageN` 时，静默预加载 `PageN+1` 的关键资源（特别是大图）。可以在 `onShow` 回调中触发下一页图片的 `preloadImage`。

2.  **JS 执行优化**
    *   **现状**: `PageManagerProvider` 中的 `wheel/touch` 事件监听虽然有 cooldown，但仍运行在主线程。
    *   **建议**: 考虑使用 Passive Event Listeners (已使用 `passive: false` 因为需要 `preventDefault`，这是权衡)。对于纯展示动画，尽量移除 JS 定时器 (`setTimeout` 动画序列)，改用 CSS Animation Delay 或 Web Animations API，减少 JS 线程占用。

3.  **Bundle 细粒度拆分**
    *   **现状**: 页面级拆分已做。
    *   **建议**: 检查第三方库（如 `recharts` 在 Page6/11/14 中使用）是否被重复打包或过早加载。如果图表只在特定页面出现，确保它们只在该页面的 Chunk 中。

4.  **DOM 节点数控制**
    *   **现状**: `pages-wrapper` 保留了所有已渲染的页面 (`isActive` 逻辑目前是 `page <= showUpTo`)。这意味着用户滚到第 20 页时，前 19 页的 DOM 都在内存中。
    *   **建议**: 实现“虚拟滚动”或“DOM 回收”机制。只保留当前页、上一页和下一页的 DOM，其他页面卸载或 `display: none` (React 中由 Key 控制卸载)，减少内存占用和样式重计算开销。
