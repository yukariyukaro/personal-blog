## 一、通用实现（先能背对）

项目里 [util.js](../../tripleuni-frontend-wechat/utils/util.js#L21-L46) 的实现是标准样式：

```js
// 节流：时间戳版，第一次必须立即执行，之后 gapTime 内只执行一次
function throttle(fn, gapTime = 1500) {
  let _lastTime = null;
  return function () {
    const _nowTime = +new Date();
    if (_nowTime - _lastTime > gapTime || !_lastTime) {
      fn.apply(this, arguments);
      _lastTime = _nowTime;
    }
  };
}

// 防抖：delay 版，每次触发都重置计时器，只有停止触发 gapTime 后才执行
function debounce(fn, gapTime) {
  let timer = null;
  return function () {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, arguments), gapTime);
  };
}
```

**一句话区分**：
- **防抖（debounce）**：关心"最后一次触发"，连续触发只认停止后的那次 → 适合**输入停止后再发请求**（搜索联想、表单校验）。
- **节流（throttle）**：关心"触发频率上限"，无论触发多密，单位时间内最多执行一次 → 适合**持续高频事件**（scroll、resize、进度回调）。

## 二、搜索功能：联想请求的防抖改造（✅ 已落地）

### 2.1 改造前的问题（口述起点）

初版（AI 生成）的 `onInputKeyWord` 是**每个键入直接请求**联想接口：`bindinput` 每次触发 handler → 立即调 `getSearchSuggestion()`。快速打字输入"university"十个字母，就是十个并发请求，其中前九个的结果都是过时的，还伴随旧结果闪回接口延迟的竞态问题。

我在体验走查时发现打字快的时候联想框会闪旧结果，就把「输入无防抖」连同竞态校验一起列入了改造项。

### 2.2 改造后的实现（✅ 口述依据）

改造只动一个 handler + 一个请求函数，其余逻辑不动。修改后的 `search.js` 关键代码：

```js
// 引入现成的防抖工具（util.js 里已有 debounce）
const utils = require('../../utils/util.js')

// 对联想请求本身做 400ms 尾随防抖：连续键入只保留最后一次
const getSearchSuggestionDebounced = utils.debounce.call(null, function (that) {
  that.getSearchSuggestion()   // 取号/竞态校验都封装在 getSearchSuggestion 内（见 2.4）
}, 400)

onInputKeyWord: function (e) {
  // ① setData 不参与防抖：输入框受控，key_word 必须即时更新，否则打字卡顿
  this.setData({
    key_word: e.detail.value,
    result_shown: false,
    page: 0,
  })
  if (this.data.key_word) {
    // ② 只有网络请求走防抖
    getSearchSuggestionDebounced(this)
  } else {
    // 输入清空：直接清联想列表，并作废在途请求的结果
    this.search_request_id = -1
    this.setData({
      search_list_loaded: false,
      search_suggestion_list: []
    })
  }
},
```

### 2.3 防抖改造的三个关键点（追问必考）

1. **防抖只包请求，不包 `setData`**：`key_word` 必须立即更新到 data（输入框受控），否则打字会卡；防抖对象是 `getSearchSuggestion`，不是整个 handler。
2. **尾随执行（trailing edge）就够**：用 400ms 纯 trailing——联想场景用户宁可等 300ms 也不想要抖动的中间态，leading 反而多打一枪继续会命中旧值。
3. **防抖挡不住在途请求**：已在飞的那个旧请求拦不住，必须配合回包竞态校验（见 §四），否则"univ"的迟到回包照样覆盖"universities"的新结果。

**为什么是防抖而不是节流**：搜索输入期望的行为是"**用户停下来之后再查**"，最后一个词最准确；节流会是"每 N ms 查一次"，中间态请求全是浪费。而滚动 loading 的期望是"**到位置就查**"，用锁控制并发即可。**防抖管"停"，节流管"频"——这两个例子正好各占一边。**

### 2.4 配套落地：回包竞态校验（防抖挡不住的部分）

防抖只降低发起频率，已在途的旧请求拦不住，所以同时给联想请求加了**单调 requestId 竞态校验**（小程序 `wx.request` 没有 AbortController，这是唯一干净的做法）：

```js
// 页面实例上维护单调递增 id（onLoad 时初始化 this.search_request_id = 0）

// getSearchSuggestion 里：发起前取号，回包后验号
getSearchSuggestion() {
  const my_id = ++this.search_request_id      // 取号：每发一次请求 id +1

  newRequest("/info/searchsuggestion", { key_word: this.data.key_word }, ...)
    .then((res) => {
      if (res.code !== 200) return
      // 竞态校验①（主防线）：不是最新一次请求 → 迟到的旧回包，丢弃
      if (my_id !== this.search_request_id) return
      // 竞态校验②（兜底）：输入已被用户改掉/清空 → 基于过期关键词的结果，丢弃
      if (this.data.key_word !== res_key_word_from_result) return
      // 两条都过才 setData
      this.setData({ search_list_loaded: true, search_suggestion_list: temp_list })
    })
}
```

**双保险的分工**：requestId 解决"乱序"（两次请求谁新谁旧），key_word 比对兜"清空/换词后的在途包"；两条都过才把结果渲染上去。演示时可以画一条时间线：`d(1) → de(2) → dev(3)`，3 先回、1 后回，1 被 requestId 一票拦掉。

## 三、滚动功能：节流等价物 —「状态锁 + 阈值」

### 3.1 搜索页的翻页触发（✅ 源码可证）

[search.js#L350-L388](../../tripleuni-frontend-wechat/pages/search/search.js#L350-L388)：

```xml
<scroll-view bindscrolltolower="onLoadMore" bindscroll="bindScroll" ...>
```

```js
onLoadMore: function () {
  if (this.data.is_loading_more) return   // ① 请求锁：同一时刻只允许一个分页请求在飞
  if (this.data.is_last) return           // ② 终止标记：到底后不再请求
  this.setData({ is_loading_more: true, page: this.data.page + 1 });
  this.getBySearch();                     // 请求回来后置 is_loading_more = false
},

bindScroll: function (e) {
  this.setData({ focus: false })
  if (this.data.is_loading_more) return;
  if (e.detail.scrollHeight - e.detail.scrollTop < 3500) {
    this.onLoadMore()                     // ③ 阈值：距底 3500px 就预加载下一页
  }
}
```

首页 [home.js#L66-L75](../../tripleuni-frontend-wechat/pages/home/home.js#L66-L75) 是同款结构（`is_loading_more` 锁 + `scrolltolower` / 距底阈值）。

### 3.2 这三件套为什么等价于节流（追问核心）

被问"你们的节流怎么做"时：

> "我没有用时间戳节流，我用的是**状态锁（is_loading_more）+ 距底阈值（3500px）+ 终止标记（is_last）**三件套。`bindscroll` 在滚动过程中高频触发，但锁保证同一时刻最多只有一个分页请求在飞——`setData` 置位 → 请求 → 回包置回 false，这个周期通常远大于两次滚动事件的间隔，所以请求频率天然被 clamp 在'一个 RTT 一次'以内。**

和纯时间节流的差异：

| 维度 | 时间戳节流 | 状态锁方案 |
|---|---|---|
| 衡量什么 | 物理时间 | **在途请求是否完成** |
| 慢网络下 | 定时器到了照样发，请求会堆积 | 上一个没回来就不发，**自动降频** |
| 快网络下 | 每 gapTime 才发一次，浪费 | 请求完成立刻解锁，**自动提频** |
| 代价 | 简单 | 需要保证异常路径（fail / reject）也要解锁，否则一次失败就永久锁死 |

关键结论：**状态锁比时间节流更适合"分页请求"这个场景，因为它锁的是资源（一个请求周期）而不是时间**。慢网自动降频这一点是纯时间节流做不到的。

### 3.3 快照里的一个真实瑕疵（可主动指出，加分）

`bindScroll` 里第一行的 `this.setData({ focus: false })` **没有锁护**——每次 scroll 事件都会执行，即使 `focus` 已经是 false 也照样 setData，滚动过程中产生大量无效渲染调度。正确做法：

```js
if (this.data.focus) this.setData({ focus: false });
```

或用浅比较/短路条件挡掉无变化 setData。这正是"节流思想不只是省请求，还要省 setData"的例子。

### 3.4 首页 3000 vs 搜索页 3500 阈值不一致

两页阈值不同（首页按项目深读文档为 3000，搜索页为 3500）。被问到就答：阈值是按"一屏高度 + RTT 内滚动距离"各页单独调的，搜索页图片卡片更重、建议提得更早，属于经验值，理想做法是统一沉淀成配置常量——本质是阈值一致性问题，可以归入待改进项。

## 四、请求去重与竞态：搜索场景的组合拳

参考 segmentfault 那篇《处理重复请求》，结合本项目可组织成三层拦截，从早到晚：

| 层 | 拦什么 | 项目里的手段 | 状态 |
|---|---|---|---|
| 1. 发起前 | 高频输入产生的重复请求 | 防抖 400ms（联想）✅ / 状态锁 `is_loading_more`（滚动）✅ | ✅ 已落地 |
| 2. 回包后 | 旧请求结果覆盖新结果 | requestId 单调校验 + key_word 双保险（见 §2.4） | ✅ 已落地（联想侧） |
| 3. 在途中 | 同 key 的重复并发请求 | 请求 Map：以 key_word 为 key，命中则不重复发 | ⬜ 未做（防抖 + 锁覆盖了绝大部分场景） |

**口述话术**：

> "防抖和节流解决的是**发起频率**问题，但拦不住两个已在途的历史请求乱序回来。所以完整的请求治理是三层：发起前用防抖/锁降低频率，回包后用 requestId 竞态校验兜底（小程序没有 AbortController，取消请求做不到，唯一干净的做法就是回包验号）；同 key 并发去重表是第三层，防抖加锁之后命中它的场景已经很少，属于优先级最低的锦上添花。"

**竞态为什么会出事（举实例子）**：
- 搜索翻页：page=2 的请求比 page=1 先回来，`one_list` 先 append page2 再 append page1，**结果顺序错乱、内容重复**。这就是为什么 `onLoadMore` 必须在锁内串行++page，而不是并发发起。
- 防抖后的联想竞态：输入 "univ" 的请求 800ms 内没回，改成 "universities" 的请求先回了，旧请求的回包晚到会覆盖新结果——用回包比对 `key_word` 解决（或者维护一个单调递增的 requestId，只认最新）。

## 五、八股追问防线（对照项目自问）

| 会被问 | 怎么答（结合项目） |
|---|---|
| 防抖和节流区别，项目中哪里用哪个 | 两者都落了：搜索联想→400ms 尾随防抖 + requestId 竞态校验（§2.2/§2.4）；列表翻页→状态锁（等价节流，锁的周期是 RTT，慢网自动降频） |
| 你的 debounce 给搜索能直接用吗 | 不能直接套整 handler：setData 更新 key_word 必须保持即时，只包网络请求。这是初学者最常见的踩坑点 |
| throttle 用 underscore 版还好用吗 | 分页场景**不行**：固定 gap 在慢网下会堆积请求（gap=1.5s、RTT=4s 时会同时飞 2~3 个请求），所以用"在途锁"代替时间锁 |
| 请求锁怎么保证解锁 | 解锁必须放在 fail/reject 路径上——参考 [request.js](../../tripleuni-frontend-wechat/utils/request.js)，如果 `getBySearch` 失败（网络抖动、reject），`is_loading_more` 不会置回 false，翻页就永久锁死。所以改造时要保证 fail 分支也置回锁位，或者用 finally 语义兜底 |
| 竞态请求乱序怎么处理 | 防抖（输入，降低频率）+ 回包 requestId 单调校验 + key_word 双保险（§2.4）三层方案；翻页侧靠状态锁保证天然串行 |
| 防抖第一次触发要不要立即执行（leading/trailing） | 项目取 trailing：联想要的是"停下来之后"的结果，leading 反而多打一枪 |
| 从"用户打字 → 网络抖动"过整个链路 | bindinput → setData（即时更新 key_word）→ debounce(400ms) → 停止后发联想请求 → 回包竞态校验（比对当前 key_word）→ 不一致丢弃 / 一致渲染。三道闸（防抖、去重、竞态校验）分别管发起、在途、回包 |

## 六、收尾：一句话立骨架

> "防抖和节流是手段不是目的，目的都是**让请求频率和用户实际需要匹配**。我项目里的整体做法是：输入用防抖、翻页用在途锁、回包用 requestId 竞态校验——三道闸一起上才能既省流量又不出乱序。防抖改造是我 code review 时识别出输入无防抖、再自己补上的，细节在 §2.2 / §2.4。"
