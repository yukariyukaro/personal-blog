
## 一、数据采集

### 1.1 采集了哪些指标

原则：**不自己用 `Date.now()` 算首屏，全部走项目已有的统一监控入口。** H5 在容器里，起点在容器初始化、HTML 下载、PIA 预取，自己打点根本拿不到起点，算出来的既不是首屏也不是渲染耗时。

| 想知道 | 口径 / 指标 | 来源 |
|---|---|---|
| 秒开率（页面多久可用） | `Monitor.reportPageReady()` 时机 ≤ 1s 的占比 | Babus `pageready`，页面侧在 `status === 'data' && hasCoreContent` 后上报 |
| FMP（首屏真实内容出现） | `.bfmp` 节点 + `babus-fmp="true"`，由 `@piajs/plugin-fmp` 采集 | `pia.config.ts` 的 `fmp({ id: 'root', attributeName: 'babus-fmp' })` |
| 预取是否命中、预取耗时 | `getPrefetchMetrics()`，耗时取 `WRD` 或 `PPE - PPS`，附 `prefetchHit` / `prefetchMode` / `prefetchCode` | `apis/report/prefetchMonitor.ts` |
| PIA 链路整体 | `getPerformanceMetrics()` / `getPrefetchRuntimeInfo()` / `getSnapshotRuntimeInfo()` / `HTML_START` / `BABUS_FMP` / `TOTAL_PREFETCH_LATENCY` | `PageLayout` 统一触发 `reportPIAMetrics()` |
| 接口成功率与耗时 | `latency` + `retStatus` / `retCode` / `bizCode` / `logId` | `Monitor.reportRequest` ← `monitorRequest` 统一封装 |
| 资源加载异常与重试 | `pia_assets_retry` / `pia_assets_retry_success` / `pia_assets_retry_fail` | `pia.config.ts` 的 `assetsRetry` |
| 体积与包构成 | 构建产物报告 + sourcemap 拆包 | 构建分析，非线上 |

**为什么秒开率的"止点"定义为 `hasCoreContent` 而不是组件挂载**：内容是自动生产的，存在「接口 200 但标题/摘要还没生成」的中间态。按业务码就报 ready，秒开率会被这类空壳页面刷成虚假的好成绩——**指标口径和页面恢复策略必须是同一个判断**（见 3.2）。

### 1.2 两端口径不要混

| | H5（PIA） | 小程序 / Lynx 卡片 |
|---|---|---|
| 起点 | 容器 + 导航开始（`navigationStart` / PIA 的 `HTML_START`） | `appLaunch`（不含容器环境准备） |
| 止点 | 业务 ready（首屏核心内容可用）或 FMP 标记 | `firstRender` / 首屏数据 `setData` 回调 |
| 可用指标 | page_ready、FMP、prefetch 命中、PIA metrics、P75/P90 | `wx.getPerformance()` 全家族（见 tripleuni.md） |
| 自补项 | 无（统一监控已覆盖） | `wx.request` 的 `profile`（DNS / TCP / TLS / TTFB） |

> ⚠️ Web 端 Core Web Vitals 官方判定看 **P75**，小程序侧常看 **P90**；两端不通用。报数必须带口径和维度（机型、冷热启动、网络、版本、缓存命中、实验分组）。

### 1.3 那些"看起来像性能数据"的坑

| 坑 | 说明 |
|---|---|
| Lighthouse 分数当线上指标 | Lighthouse 是实验室（lab）数据；线上要看真实用户（field）分位。两者不能混着讲 |
| page_ready 早于真实内容恢复 | 若在骨架屏阶段就报 ready，秒开率会被"美化"，但用户体感没变好 |
| 漏掉 prefetch 命中维度 | 命中与未命中是两条路径，混在一起算，优化效果会被稀释 |
| 只看均值 | 性能是长尾分布，一个卡 6 秒的用户能把十个人均值抬到没人真正体验到的位置（见提纲附录 B） |

### 1.4 一分钟口述版

> 「秒开率我不自己打点。H5 跑在容器里，起点在容器初始化和 HTML 下载之前，`Date.now()` 根本拿不到起点，算出来的不是首屏。项目里走的是统一监控：页面在『首屏核心内容可用』时调 `reportPageReady`，同时渲染一个 `babus-fmp` 隐藏节点给 PIA 的 FMP 插件，另外 PIA 还会统一上报预取命中、预取耗时、`TOTAL_PREFETCH_LATENCY` 这些字段。
>
> 这里有个细节我特意对齐过：ready 的条件不是『接口返回成功』，而是『接口成功且标题、摘要非空』。因为内容是自动生产的，存在 200 但内容还没生成的中间态——按业务码报 ready，秒开率会被空壳页面刷得很好看，但用户看到的就是个空架子。指标口径和页面兜底策略必须是同一个判断。」

### 1.5 追问防线

| 会被问 | 怎么答 |
|---|---|
| Web 端首屏加载时间怎么拿？ | 标准口径是 `PerformanceNavigationTiming`（navigationStart → domContentLoaded / loadEventEnd）+ FP/FCP（paint 条目）+ LCP（`PerformanceObserver` 订阅 `largest-contentful-paint`）。端内 H5 还要叠加容器侧阶段（webview 初始化、资源加载、JSB 注入），这部分只有 hybrid devtools 能看 |
| 起止时间怎么确认？ | 起点不能用业务 JS 执行时刻（已偏晚）；止点不是整页 load，而是首屏关键内容可用。项目里止点就是 `status==='data' && hasCoreContent`，与 FMP 标记同一条件 |
| 那 LCP 和秒开率是一回事吗？ | 不是。LCP 是浏览器侧的内容绘制指标，秒开率是业务侧"页面可用"的占比。简历里写的 `LCP ≤ 1s` 与项目内 page_ready ≤ 1s 的关系**待确认**，讲的时候要统一到同一个口径 |
| 小程序里怎么记录加载起止？ | 原生小程序走 `wx.getPerformance()`：`appLaunch` 给冷启动总耗时，`firstRender` 给首次渲染，`evaluateScript` 给注入耗时；自补一块是 `wx.request` 的 `profile`。Lynx 卡片侧对应能力**待确认** |
| 埋点会不会拖慢首屏？ | 攒批、异步、失败不重试、不在渲染路径同步等待；PIA/Babus 的上报本身在 `PageLayout` 层统一触发，页面不额外采集 |

## 二、怎么找瓶颈

> 一句话：**瓶颈通常不在"哪一段最慢"，而在时间轴上的空白和串行。**

### 2.1 工具分层：一个工具回答一个问题

| 层 | 工具 | 回答什么问题 | 局限 |
|---|---|---|---|
| ① 线上分位 | Babus / PIA metrics 看板 | 秒开率、FMP、预取命中的 P75 / P90 在什么机型、版本上回退 | 只有数值、没有时间轴，定位不到"谁在等谁" |
| ② 阶段耗时 | **lighthouse + hybrid devtools** | 各阶段耗时分布：TTFB、加载延迟、加载时间、呈现延迟分别占多少 | lab 数据 ≠ 真实用户；容器阶段要 HDT 才看得到 |
| ③ 体积构成 | **构建产物报告 + sourcemap 拆包** | 首包里到底是谁占了体积、哪些是真进首屏的 | 只说体积，不直接等于耗时 |
| ④ 网络瀑布 | HDT 网络面板 | 接口、静态资源的起止与串行关系 | 单机采样 |
| ⑤ 定点埋点 | `prefetchMonitor` / `reportRequest` | 预取命中率、接口 TTFB 与错误码 | 只看请求层 |

②③ 是本次**同期并行**做的两套分析：耗时看"时间花在哪一段"，体积看"东西是从哪来的"，两者对不上时往往能互相验证（例如耗时集中在下载，而体积分析显示是基座 SDK）。

### 2.2 用 LCP 四段对号入座

Lighthouse 把 LCP 拆成四段，本次三段都有明确落点：

| 子段 | 本项目对应什么 | 本次结论 |
|---|---|---|
| **TTFB** | 容器初始化 + HTML 下载（SSR 后 HTML 里已带首屏数据） | SSR 直接削掉"客户端发起首屏接口"这一段 |
| **加载延迟** | TTFB → 首屏内容开始渲染，**首屏数据请求的往返** | 优化前的主要瓶颈：数据要在客户端拉完才渲染 |
| **加载时间** | 首屏 JS / CSS 下载 | 订阅弹窗整棵子树曾无条件进首包 |
| **呈现延迟** | React 渲染 + 水合 | 需要保证水合首轮结构一致，否则会重建 DOM |

### 2.3 本次定位到的三个瓶颈

**瓶颈 1：首屏数据要走一次客户端往返（加载延迟）**
客户端首屏必须等接口返回才能渲染，用户先看到骨架、再看到内容。`onShellReady` 一就绪就能开始吐 HTML 的流式 SSR 正好压这一段（PIA 的 `string-stream` 模式，底层 `renderToPipeableStream`）。

**瓶颈 2：与首屏无关的大子树进了首包（加载时间）**
订阅弹窗体系（三个面板变体 + 发奖弹窗）是本页体积最大的一块视图，而它在 SSR 首屏时两个显隐状态都是 false——**永远不该进首屏**。构建产物报告确认了它的占比，于是从静态 import 改为 `React.lazy` + 条件挂载。

**瓶颈 3：全站基座 SDK（天花板）**
拆包后发现页面独占资源只有 JS 28.4 KB + CSS 8.4 KB，**占首包 7%**；其余 480 多 KB 全是全站共享基座。最大一块 `2066.js` 174.9 KB gzip、100% 加载，经 sourcemap 拆解全部来自 node_modules：rrweb 会话录屏、crypto-js、pako、`@slardar/web`。
→ **结论：这一页能动的只有那 36.8 KB，继续优化必须跨团队治理基座**。这个结论本身就是产出。

### 2.4 顺手排除掉的方向（确认什么"不慢"）

| 假设 | 怎么排除 |
|---|---|
| 是渲染太重？ | 页面首屏结构固定、无长列表，体积拆解显示 CSS 只有 8.4 KB；瓶颈不在渲染计算 |
| 是图片太大？ | 首屏无大图依赖（指数分时图是异步补齐的，不阻塞首屏） |
| 是接口慢？ | 接口走了统一 `reportRequest` 监控，`latency` 分布正常，问题在"发得太晚"而不是"回得太慢" |
| 是 SSR 反而更慢？ | SSR 降级路径（CSR 静默恢复）保留，未命中 SSR 时行为与纯 CSR 一致，没有把体验押在 SSR 单点上 |

### 2.5 现象 → 量法 → 结论 速查表

| 现象 | 用什么量 | 定位到的瓶颈 |
|---|---|---|
| 首屏白屏久、骨架屏停留长 | 线上秒开率/FMP 分位 + HDT 阶段耗时 | 首屏数据要走客户端往返（加载延迟） |
| 首包大、下载慢 | 构建产物报告 + sourcemap 拆包 | 无关子树进首包 + 基座 SDK（后者超出本页范围） |
| 首屏出来了但内容空 | 秒开率与内容就绪字段交叉看 | 自动生产的中间态被误判为成功（→ 3.2） |
| 指数模块时有时无 | 指数三态派生 + 恢复重试日志 | 缺失被当成"不展示"（→ 3.3） |

## 三、优化策略

### 3.1 SSR 接入：把首屏数据请求前移到服务端

**做了什么**：页面在 `pages.config.ts` 声明 `ssr: { mode: 'string-stream' }` 与双端 prefetch；服务端预取函数归一化 query、透传上下文、请求主接口，结果由 PIA 序列化注入 HTML，客户端转成 `preloadedState` 直接进 data 态。

**压的是哪一段**：加载延迟（首屏接口往返整段消失）+ TTFB（HTML 里已带数据，不需要等 JS 再发请求）。

**流式（string-stream）的意义**：相比 `renderToString` 一次性返回整段 HTML，`renderToPipeableStream` 在 `onShellReady` 后就能开始写入 chunk——**用户不用等所有数据渲染完才看到东西**。PIA 在 `getServerRender` 里做的就是建流、并用 transform stream 注入 prefetch 降级等运行时代码。

**代价与配套**：
- 水合一致性成了新 bug 来源：开户 Portal 底栏依赖 `document`、分享入口依赖客户端 `aid`，都要"首轮输出同构、effect 后再切换"；
- Mock 旁路：非生产且显式带场景标识时才绕过默认 dataLoader（平台侧能力补齐后应删除）。

### 3.2 两层成功判定：性能优化不能只换来"更快的空壳"

**问题**：自动生产链路上存在「接口 200 但内容还没生成」的中间态。若按业务码判成功，页面直接进 data 态，用户看到有骨架没内容的壳；更糟的是**已进数据态，客户端恢复逻辑不会再跑**，页面就永远停在那里。

**做法**：`业务码成功 && headerInfo.title 与 brief 非空` 才算首屏成功，否则走与 SSR 降级同一条恢复链路（`refreshPageData({ silent: true })`）。

**为什么"silent"**：降级时页面已经渲染了骨架，把状态清成 loading 会让骨架闪一次再回来，比不闪更糟。代价是恢复期间没有明确加载态，当前也没有超时兜底。

**和采集口径的关系**：秒开率的 ready 条件用的是同一个判断——**指标、渲染分支、恢复策略三者同源**，不会出现"指标很好但用户看到空壳"。

### 3.3 三类补齐与静默恢复：让性能优化不牺牲完整性

| 补齐 | 依赖 | 失败语义 |
|---|---|---|
| 自选状态、基金 schema | 依赖主数据，串行 | 失败只打 console，线上不可见（**已识别缺口**） |
| 订阅资源位 | 不依赖主数据，并行 | 独立请求，失败不影响首屏 |
| 指数描述符恢复 | 主接口窄重取，退避 1s→2 倍→上限 30s | 未知态保留骨架并持续重取，避免"还没算出来"被永久当成"不需要展示" |

**两条进入路径一套补齐逻辑**：SSR 成功（预置状态）与 SSR 降级（客户端恢复）下组件挂载时机不同，四类补齐收在同一个 hook、统一以数据态为触发条件，避免出现"只在其中一条路径生效"的分支——这类 bug 在本地（SSR 正常）根本不会暴露。

**窄更新而非整体覆盖**：指数恢复打的是完整主接口，但落库只合并指数段，否则会打掉并行补齐的自选状态和基金配置，用户可见地"自选变回去了"。

### 3.4 懒加载：把永远不进首屏的东西拆出去

```jsx
{subscriptionPopupVisible || subscriptionPrizeDialog
  ? <Suspense fallback={null}>...</Suspense>
  : null}
```

技术底座是 React 18.2 原生 `lazy`，零新增依赖；SSR 首屏时两个显隐状态都是 false，弹窗 chunk 不进首屏 HTML 引用。

| 口径 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 页面自有首屏 JS（gzip） | 28.4 KB | 19.5 KB | −8.9 KB / −31% |
| 页面首包合计（gzip） | 517.7 KB | 504.1 KB | −13.6 KB / −2.6% |

两个百分比必须一起给：只说 31% 会让人以为整页快了三成，只说 2.6% 会显得没做什么。

**验证方式（比看分析图更硬）**：构建后检查该异步 chunk 在页面产物中的引用次数为 0——它直接回答"首屏会不会加载它"。拆出的 async chunk 为 12 KB gzip / 38 KB raw。

### 3.5 没做和不该做的

| 手段 | 状态 |
|---|---|
| 容器预加载 / 预取 / Snapshot | 平台侧能力，本页未接；属于"还能做但不在这一轮" |
| 分包 / 基座 SDK 瘦身 | 涉及跨团队与数据完整性风险，只做到提出 |
| 首屏请求超时兜底 | **未做**：CSR 恢复没有超时上限，很慢时会显得卡住 |
| 退避次数上限 | **未做**：永远不关联指数的内容会一直重试到页面关闭 |

## 四、数据回收与实验

### 4.1 性能指标：秒开率 10% → 约 75%

口径：页面 1 秒秒开率（**LCP ≤ 1s**，简历口径；项目内对应 page_ready / FMP ≤ 1s —— 两者关系**待确认**）。

| 项 | 值 |
|---|---|
| 基线 | 10% |
| 优化后 | 约 75% |
| 手段 | SSR 首屏直出 + 订阅弹窗懒加载 |
| 分析工具 | lighthouse + hybrid devtools（阶段耗时）、构建产物报告 + sourcemap（体积） |

> ⚠️ 报数时必须一起说清楚：是实验室值还是线上分位、分母是否过滤异常 PV、周期多长、是否同期还有别的不相关改动。

### 4.2 用户影响：A/B 实验

| 指标 | 结果 |
|---|---|
| 页面点击转化率 | 提升约 10% |
| 页面到达率 | 提升 5% |

**为什么看"到达率"**：它直接对应"用户有没有等到页面出来"——首屏越快、白屏越短，中途退出的人越少。这和性能改动是同一因果链上的指标，比看停留时长更干净。

**AA 与 AB 的关系**：AA 是上 AB 之前的一致性校验（两组同策略，若跑出显著差异说明分流有问题，SRM），它本身不是效果度量；效果由 AB 给出。

### 4.3 业务量

落地页日均 1000+ UV，日促 20+ 用户开户、10+ 用户交易。

> 这三项是业务量口径，和性能提升之间**没有做因果归因**，讲的时候不要连成"因为优化了首屏所以开户变多"。

### 4.4 三个必须避开的坑

1. **幸存者偏差**：表现差的用户已经关掉页面了，不会再产生数据。只看"留下来的人"等于把问题消灭在口径里——所以要盯到达率这类与流失直接相关的指标，而不是只盯停留时长均值。
2. **口径混用**：实验室 vs 线上、P75 vs P90、含异常 PV vs 不含，答案完全不同。
3. **非随机分组当因果**：另有一次"承接页用户次日回访 40% vs 其他用户 3%"的对比，因分母口径错配（其他用户用了全站活跃用户）、回访事件未对齐同一页面同一动作、以及承接页本身在行情 tab 内存在用户自选择，该结论被弃用。**技术口径要前置定义：两组分别是谁、分母是什么、事件怎么算。**

## 五、非常规手段

以下为体系里存在、本页未接入的"下一步"，答辩时作为"我知道还能怎么压"来讲，不要说成已做：

| 手段 | 原理 | 压哪一段 |
|---|---|---|
| 容器预加载 / 预取 | 客户端在打开页面前提前创建 WebView、预请求首屏数据（PIA Prefetch 把请求从 WebView 启动前就发起） | 加载延迟（整段前移） |
| Snapshot | 缓存页面 DOM/HTML，二次进入先展示缓存再更新 | 呈现延迟 |
| NSR | 在 PIA Worker 中提前执行渲染逻辑生成 HTML | TTFB + 加载延迟 |
| 首页预加载 / codeCache | 在登录页等前置页面预加载目标页资源、预热字节码缓存 | 加载时间 |
| 服务端接口合并 | 首屏多接口合成一次往返 | 加载延迟 |
| preconnect / preload | 提前完成 DNS/TCP/TLS、提前拉取后发现的资源 | TTFB / 加载时间 |
